System Deployment Guide

This archived guide describes deploy:system at v0.8.5 source commit 7632c915. These commands and defaults are historical instructions, not the current operator workflow or a claim of live deployment compatibility.

Prerequisites

  1. Copy .env.example to .env and configure the required variables
  2. Ensure you have sufficient funds in the deployer wallet

Environment Configuration

Configure the archived task’s variables below. TEAM_DEPLOYER selects the first signer on networks using createNetworkConfig; unset values fall back to the configured dummy key unless keystore mode is enabled. The local docker entry omits an accounts list and uses the node’s exposed accounts. Leave ADMIN_PUBLIC_KEY empty for unmodified fresh setup: selecting a different admin does not automatically give the actual deployer every specific setup role (for example, registerHook requires INTEGRATION_ADMIN_ROLE). Separate governance requires explicit setup-role provisioning and a reviewed authority handoff/cleanup. 

# For key-configured HTTP networks: the explicit deployer private key
TEAM_DEPLOYER="0x..."

# Optional: leave empty for the archived task’s admin=deployer setup assumption
ADMIN_PUBLIC_KEY=""

# Optional: Fee receiver address (defaults to admin)
SYMMIO_FEE_RECEIVER=""

# Optional: Existing collateral token address
# If not set, a FakeStablecoin will be deployed (useful for local testing)
COLLATERAL_ADDRESS=""

# Deploy SymmioSymbolManager (default: true, set to "false" to skip)
DEPLOY_SYMBOL_MANAGER="true"

# Deploy SymmioPartyB contract (default: true, set to "false" to skip)
DEPLOY_PARTYB="true"

# Optional: Signer address for SymmioPartyB (ERC-1271 signature verification)
PARTYB_SIGNER=""

# Register a dummy affiliate for testing (default: true, set to "false" to skip)
REGISTER_DUMMY_AFFILIATE="true"

# Setup InstantLayer templates for OpenPosition and ClosePosition flows
# (default: true, set to "false" to skip)
SETUP_INSTANT_LAYER_TEMPLATES="true"

# Optional: existing MuonSignatureVerifier address
# If empty, deploy:system deploys a new MuonSignatureVerifier
MUON_SIGNATURE_VERIFIER_ADDRESS=""

# Optional: Muon app/runtime config on Diamond
# If set, deploy:system calls setMuonIds(muonAppId)
MUON_APP_ID=""
# Each independently defaults to 300 seconds; setMuonConfig is a checkpointed setup step
MUON_UPNL_VALID_TIME=""
MUON_PRICE_VALID_TIME=""

# Optional: seed MuonSignatureVerifier keys/signers
# addPublicKey is called only when BOTH are set
MUON_PUBLIC_KEY_X=""
MUON_PUBLIC_KEY_PARITY="" # 0 or 1
# Comma-separated addresses, e.g. "0xabc...,0xdef..."
MUON_GATEWAY_SIGNERS=""

# Deployment log level: "silent" (default), "minimal", or "verbose"
DEPLOY_LOG_LEVEL="minimal"

Deployment

Local Anvil Deployment (Recommended for PartyB Testing)

  1. Start a local Anvil node:
anvil #or "anvil --disable-code-size-limit" if you see the limit problem
  1. Configure .env for local testing (minimal config):
# Archived local HTTP network: docker. It uses the node’s exposed accounts.
HARDHAT_DOCKER_URL="http://127.0.0.1:8545"
# To select a particular private key locally, first configure that network’s
# accounts explicitly (for example [process.env.TEAM_DEPLOYER!]).
# Setting TEAM_DEPLOYER alone does not change the archived docker entry.
  1. Run the deployment:
npx hardhat deploy:system --network docker

Testnet/Mainnet Deployment

npx hardhat deploy:system --network <NETWORK_NAME>

Checkpoint System (Resumable Deployments)

The deployment system supports checkpointing for resumable deployments. If a deployment is interrupted (network error, out of gas, etc.), the checkpoint is a progress hint, not receipt or post-state proof. Several setup actions save their flags after transaction submission without waiting for a successful receipt. Reconcile submitted setup transactions and intended roles/configuration before trusting flags or resuming. Interrupted diamond cuts additionally require full selector-to-facet reconciliation.

How It Works

  • Checkpoint files are saved to tasks/data/checkpoints/checkpoint-<chainId>.json
  • Steps are checkpointed when their action returns. For setup actions that return after broadcast, this can precede mining and successful execution.
  • Resume skips steps flagged complete, without proving every receipt or intended setup post-state. Confirm those outcomes independently; repair a stale flag only after reconciliation.
  • Diamond-cut recovery uses incomplete on-chain heuristics; verify every expected selector/facet before treating an interrupted cut as complete

Commands

# Resume from existing checkpoint (default behavior)
npx hardhat deploy:system --network <NETWORK_NAME>

# Force fresh deployment, ignoring any existing checkpoint
npx hardhat deploy:system --network <NETWORK_NAME> --fresh

Checkpoint Status Display

When resuming, you'll see a status display showing:

  • Network and chain ID
  • When the deployment started and was last updated
  • Which contracts are already deployed
  • Setup progress (roles granted, parameters set, etc.)

What Gets Deployed

The deploy:system task deploys and configures the following contracts:

  1. Collateral - FakeStablecoin (or uses existing if COLLATERAL_ADDRESS is set)
  2. Diamond - Main protocol contract with 29 facets including DiamondCutFacet, and 4 linked libraries
  3. MuonSignatureVerifier - External Muon verification contract (or uses MUON_SIGNATURE_VERIFIER_ADDRESS if provided)
  4. AccountLayerDiamond - Unified account/affiliate management with 6 application facets, plus cut/loupe infrastructure
  5. InstantLayer - Instant settlement layer for batched operations
  6. SymmioSymbolManager - Optional, default-on symbol manager (DEPLOY_SYMBOL_MANAGER)
  7. SymmioPartyB - PartyB contract (optional, if DEPLOY_PARTYB=true)
  8. AccountManager - For dummy affiliate (optional, if REGISTER_DUMMY_AFFILIATE=true)

  • AccountLayer is registered as the system hook on Diamond (registerHook(address(0), accountLayerDiamond))

Muon Signature Verifier Setup

When deploy:system runs:

  • If MUON_SIGNATURE_VERIFIER_ADDRESS is set, this archived task records and uses the supplied address directly; it does not preflight contract code or capability support.
  • Otherwise, a new MuonSignatureVerifier is deployed.
  • Diamond is wired using setSignatureVerifierAddress. This archived setter stores the address without a code or capability check; setup then reads back the configured address. No RemoveMargin capability API exists in this revision.
  • If deployer has admin on verifier, admin receives DEFAULT_ADMIN_ROLE and SETTER_ROLE on verifier.
  • If MUON_PUBLIC_KEY_X and MUON_PUBLIC_KEY_PARITY are both set, addPublicKey is called (idempotent check).
  • If MUON_GATEWAY_SIGNERS is set, each signer is added with addGatewaySigner (idempotent check). Registration does not grant category permissions: before oracle-dependent use, a verifier SETTER_ROLE holder must explicitly authorize both the key and gateway for the required historical categories (IDs 0–6) through setPublicKeyPermissions and setGatewaySignerPermissions. The task does not perform those grants. See Muon key setup.

Muon Runtime Config on Diamond

  • If MUON_APP_ID is set, setMuonIds is called.
  • MUON_UPNL_VALID_TIME and MUON_PRICE_VALID_TIME independently default to 300 seconds. Setup schedules setMuonConfig with both effective values even when neither variable is supplied.
  • Setting only one validity variable changes that value while the other remains 300; it does not skip configuration. Checkpointed completed steps can still be skipped on resume.

Muon View-Call Verification

As part of setup, deploy:system verifies Muon config by reading:

  • getSignatureVerifier() against expected verifier address.
  • getMuonIds() against MUON_APP_ID (if provided).
  • getMuonConfig() against both effective configured validity values, including the independent 300-second defaults.
  • getAllPublicKeys() / getAllGatewaySigners() on verifier (if those seed env vars are provided).

  • Admin receives DEFAULT_ADMIN_ROLE and SETTER_ROLE on InstantLayer

InstantLayer Templates (if SETUP_INSTANT_LAYER_TEMPLATES=true)

Three templates are registered. These are intended payload flows; template storage records operation counts and injection offsets rather than restricting each operation to a named selector. The task enables instantOpenMode on template ID 0, assuming the fresh registry order below.

InstantOpen Template (4 operations)

Op Function Target Dependencies
0 addMarginToNextVA AccountLayerDiamond None
1 Quote-returning sendQuote variant Diamond via AccountLayer Returns quoteId
2 lockQuote Diamond via PartyB sourceIndices [1], insertionPoints [0], sourceOffsets [0]
3 openPosition Diamond via PartyB sourceIndices [1], insertionPoints [0], sourceOffsets [0]

InstantClose Template (2 operations)

Op Function Target Dependencies
0 requestToClosePosition Diamond via AccountLayer No result injection
1 fillCloseRequest Diamond via PartyB No result injection

InstantCloseWithAllocation is the third template and contains 3 operations. All three sourceIndices, insertionPoints and sourceOffsets arrays are empty for every step. The task does not specify a third-step selector; the signed payload supplies the desired allocation operation. For InstantOpen, offsets are bytes: read the first 32-byte word from op 1 and write the first ABI argument after the later call’s selector.

PartyB Setup (if deployed)

  • SymmioPartyB is registered in Diamond
  • Admin receives DEFAULT_ADMIN_ROLE, MANAGER_ROLE, and SETTER_ROLE on SymmioPartyB
  • InstantLayer receives TRUSTED_ROLE on SymmioPartyB
  • InstantLayer is added to multicastWhitelist on SymmioPartyB
  • Signer is set on SymmioPartyB (if PARTYB_SIGNER is configured)
  • SymmioPartyB is registered on InstantLayer (registerPartyBs - also grants OPERATOR_ROLE)

Contract Verification

After deployment, verify all contracts on the block explorer:

# Verify all contracts from deployment logs
npx hardhat verify:all --network <NETWORK_NAME>

# Skip first N contracts (for resuming)
npx hardhat verify:all --network <NETWORK_NAME> --skip 10

The verify:all task reads from all deployment log files and verifies each contract.

Troubleshooting

Deployment fails mid-way

Before resuming, reconcile submitted setup receipts and verify the intended roles and configuration, as well as every selector in any interrupted cut. A saved flag can describe a transaction that was only broadcast, so do not infer successful execution from the checkpoint: 

npx hardhat deploy:system --network <NETWORK_NAME>

Checkpoint appears corrupted

Force a fresh deployment:

npx hardhat deploy:system --network <NETWORK_NAME> --fresh

Or manually delete the checkpoint file:

rm tasks/data/checkpoints/checkpoint-<chainId>.json

Role granting fails

Confirm the actual first signer selected by the archived network configuration. Key-configured networks use TEAM_DEPLOYER; docker uses node-exposed accounts unless configured otherwise. DEFAULT_ADMIN_ROLE does not imply the specific roles used by setup. The unmodified fresh flow assumes admin equals deployer; a different governance admin requires explicit setup-role provisioning and later cleanup.

Muon verifier seeding fails

If MUON_PUBLIC_KEY_* or MUON_GATEWAY_SIGNERS are set, deployer must have SETTER_ROLE on the configured MuonSignatureVerifier. If using an existing verifier where deployer is not admin/setter, seed keys/signers with a proper verifier admin account.

The archived task has no capability preflight. Independently verify that the supplied address implements the historical enum-typed verifier ABI and that registered keys and gateways hold the required seven-category permissions. Registration/readback alone does not prove a real oracle signature can validate.

Muon config was not applied

Each validity variable independently defaults to 300 seconds. The task checkpoint-schedules setMuonConfig and compares both readback values; supplying just one variable does not skip it. On resume, inspect whether the checkpoint already marked this setup step complete, then verify its receipt and both current readback values before deciding whether to repair that flag or resubmit.

Diamond cut verification mismatch

Recovery is heuristic. Core treats more than one loupe facet as completion; AccountLayer probes an admin() function absent from its archived ControlFacet. Neither proves every selector was installed, and a cut may have completed only some chunks. Reconcile every expected selector-to-facet mapping before retrying or repairing a checkpoint; mark completion only after that verification.
