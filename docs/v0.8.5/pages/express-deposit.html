Express Deposit & Withdrawal System

The Problem

SYMMIO enforces a withdrawal cooldown (typically 12 hours from the user's last deallocation) to protect against attack vectors. While essential for security, this creates real friction — users who need timely access to funds have no option but to wait. Frontends can't differentiate on withdrawal speed, and failed withdrawals due to insufficient contract balance lead to poor UX.

What We Introduced in SYMMIO Core

v0.8.5 adds Core virtual-provider integration and AccountLayer express-deposit splitting. When a user uses an express-rate deposit through an affiliate's frontend, the affiliate can configure a percentage (X%) of that deposit to be automatically routed to an external provider contract via the onExpressDeposit callback. This is built on top of the Virtual Fund System — the provider contract is registered as a virtual provider in SYMMIO and implements the IVirtualProvider lifecycle callbacks (onExpressDeposit, onWithdrawRequest, onWithdrawComplete, etc.).

The core protocol also adds the withdraw system hooks that let registered express providers accept, process, cancel, and finalize withdrawal requests through callbacks.

The deposit fee percentage is each affiliate's own decision and their own capital responsibility. SYMMIO core provides the mechanism, but the affiliate chooses what percentage to allocate. The protocol does not manage or guarantee these funds.

Implemented integration: - AccountLayer express-deposit splitting through the explicit WithExpressRate methods (configurable % per affiliate) - Virtual provider registration and callback interface - Express provider registration and withdraw lifecycle hooks (accept, complete, cancel, suspend) - Opaque providerData bytes; any option signature validation belongs to a provider

What the core does NOT provide (not yet implemented): - The actual Express and Virtual provider contracts - The off-chain bot - Withdrawal option generation and signing

The Future System: Express & Virtual Withdrawals

The remainder of this page describes an unimplemented provider/bot design for v0.8.5, not deployed behavior. Its 20-second and 12-hour examples and hourly buckets are illustrative assumptions. Core stores a configurable cooldown from the user's last deallocation; it does not implement this scheduler or guarantee provider delivery.

Overview

The proposed provider-side infrastructure consists of an Express Contract, Virtual Contract and off-chain Bot. The design targets up to three options, conditional on available liquidity and the Core request/account guards: 

flowchart TD
    A[User requests withdrawal] --> B{Bot evaluates<br/>available liquidity}
    B -->|Enough now| C["Option A: Instant<br/>(~20 seconds)"]
    B -->|Enough later| D["Option A2: Earliest-Available<br/>(between now and 12h)"]
    B -->|Not enough| E["Option B: After configured cooldown<br/>(subject to core liquidity and guards)"]

    C --> F[Express Contract fronts funds immediately]
    D --> G[Express Contract reserves funds,<br/>pays at projected time]
    E --> H[Attempt standard withdrawal after stored cooldown and required checks]

    F --> I[Claim core reimbursement after stored cooldown and required checks]
    G --> I

Option A — Instant (~20 seconds): If enough liquidity exists right now across the Express and Virtual pools, the proposed provider would front the funds. Its Core reimbursement can be claimed after the stored cooldown, subject to request status, account suspension and callback success; the example timing is not a Core delivery guarantee.

Option A2 — Earliest-Available (between now and 12 hours): When instant liquidity isn't sufficient but the Express Contract can project when enough funds will become available (based on other pending withdrawals finalizing), it offers the user a specific earlier payout time. A user might wait 2 hours instead of 12. The proposal uses a 12-bucket ring buffer of hourly slots to track expected inflows and reservations, with the goal of preventing double promises. No such scheduler or reservation invariant is implemented in the archived v0.8.5 provider source.

Option B — After Configured Cooldown: A classic request needs no provider, but creation requires sufficient user free balance and unreserved real collateral in Core. Finalization still requires an eligible request and an unsuspended user. It is not an unconditional 12-hour fallback; proposed Virtual-provider backup would also depend on that provider's implementation and liquidity.

The frontend shows the best available option. If instant is possible, show that. If not but earliest-available is, show that. Otherwise, offer the classic path only when its normal liquidity/account conditions can be met.

Components

Express Contract (proposed one per chain): The main coordinator. Manages two types of liquidity pools — a general pool available to all users, and per-frontend pools funded by frontend operators. Validates bot-signed withdrawal options, locks/reserves funds, and handles the full withdrawal lifecycle. For earliest-available withdrawals, the bucket-based scheduling is intended to avoid promising the same future liquidity to multiple users; the invariant is unverified without an implementation.

Virtual Contract (proposed one per chain per frontend): Holds the liquidity funded by the express deposit fee percentage. Locks funds when included in withdrawal requests, releases them to users on Express Contract instruction. Also would offer provider-funded backup if Core is short of collateral. Core has no automatic liquidity-shortfall switch to this provider.

Bot (proposed one globally): Off-chain orchestrator that provides the withdrawal options API, signs options with replay-protected nonces, monitors events, performs risk assessment through an anomaly detection API, and schedules processing calls at the right times.

Liquidity Priority

The proposed option-generation policy would select pools in this order: 1. Express Contract frontend-specific balance (frontend-first policy) 2. Virtual Contract frontend balance (auto-funded from deposits) 3. Express Contract general balance (system-wide fallback)

The proposed after-cooldown policy prefers Core liquidity, then Virtual-provider liquidity. This fallback is not implemented by Core; classic requests still require unreserved real collateral at initiation.

Proposed Safety Properties

  • Proposed permissionless provider payout: The design would allow user processing after a tolerance period if the bot is unavailable. This provider-side recovery is not implemented here. Core finalization is separately permissionless after its cooldown when request, suspension and callback guards pass; unconditional liveness is not guaranteed.
  • Proposed risk gating: The bot would check an anomaly detection API before processing instant withdrawals. Flagged users would be sent for administrative review under that provider policy.
  • Proposed replay protection: Provider options would include a per-user nonce consumed by the provider. The archived Core only stores opaque providerData; this option-nonce implementation is not supplied.
  • Conditional classic path: A provider-free request can proceed only with sufficient unreserved Core collateral and normal account/request guards. Existing provider requests do not automatically become classic requests, and proposed provider backup remains dependent on provider state and liquidity.
