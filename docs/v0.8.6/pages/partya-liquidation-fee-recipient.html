v0.8.6/Liquidation

PartyA Liquidation Fee Recipient Cleanup

PartyA liquidation LF needed one clear recipient, so final settlement pays the capped fee to the liquidation starter.

Summary

PartyA LF now has one receiver: liquidators[partyA][0], the address that started the PartyA liquidation.

Before v0.8.6, PartyA LF was split between two receivers: the caller that started liquidation and the first caller that set liquidation prices. In practice, a single liquidator now performs all liquidation steps almost every time. Competition is at the first liquidation call, not at each later step.

v0.8.6 removes the second receiver and pays the capped LF only to the starter at final settlement. The protocol monitors liquidator performance and suspends or removes bad actors when needed.

What Changed

Before v0.8.6: PartyA LF was split 50/50 between liquidators[partyA][0] and liquidators[partyA][1].

liquidators[partyA][0] was the caller of liquidatePartyA or deferredLiquidatePartyA. liquidators[partyA][1] was the first caller of setSymbolsPrice or deferredSetSymbolsPrice; later price-setting calls did not add more LF receivers.

After v0.8.6: one PartyA LF receiver. The final capped LF goes to liquidators[partyA][0] because that is the competitive step. Price setters do not receive PartyA LF.

P.S. The cap logic did not change. PartyA LF is still limited by maxLiquidationProfitPerPosition * partyAPositionsCount[partyA], and any amount above the cap goes to the liquidation insurance vault.

Final Settlement Accounting

The LF is handled during PartyA liquidation finalization, after deferred balance and reimbursement accounting have been resolved. 

// Pay capped LF to the liquidation starter.
uint256 lf = accountLayout.liquidationDetails[partyA].liquidationFee;
if (lf > 0) {
    emit SharedEvents.BalanceChangePartyA(partyA, lf, SharedEvents.BalanceChangeType.LF_OUT);
    address liquidationStarter = accountLayout.liquidators[partyA][0];
    accountLayout.allocatedBalances[liquidationStarter] += lf;
    emit SharedEvents.BalanceChangePartyA(liquidationStarter, lf, SharedEvents.BalanceChangeType.LF_IN);
}

The resulting balance movement is:

  • BalanceChangePartyA(partyA, lf, LF_OUT) for the liquidated PartyA.
  • allocatedBalances[liquidationStarter] += lf.
  • BalanceChangePartyA(liquidationStarter, lf, LF_IN) for the starter.

If the capped LF is zero, no LF balance-change events are emitted.
