Session Keys

Session keys exist for seamless one-click trading. A session key is a key pair the front end creates and the account owner authorizes once. Until the authorization expires, the key signs the operations the owner allowed, for one account, so each trade is a single click instead of a wallet approval.

What a session key is

A session key is an ordinary Ethereum key pair with its own address. It is not the owner wallet’s key and not a contract. Its only power comes from an InstantLayer delegation: an on-chain record, written by the account owner, saying this key may sign these functions for this account until this time.

The key holds no funds. Collateral and positions stay in the user’s accounts; the key only signs instructions about them. A signed operation still names the user’s account, and InstantLayer executes it as that account once it confirms the delegation.

Identity Role
Owner wallet Owns the accounts and signs the delegation grant
Session key Signs operations the grant allows, without wallet prompts
SubAccount The trading account a delegation is granted for; holds the funds
Virtual Account Holds a position and its margin under a SubAccount; covered by the SubAccount’s grant
Service signer A separate delegate, such as a conditional-order bot, with its own grant

Why use one

  • One wallet prompt instead of many. The user signs once to authorize the key. Opening and closing positions, moving margin, and approving fees are then signed by the key in the background.
  • Gasless by design. Key-signed operations are relayed by a solver or through Gasless Layer. The relayer pays the network fee, and any charge comes from the account in collateral. The user never needs native gas.
  • Narrower than the wallet. A key reaches one account family, only the functions it was granted, and only until its expiry. The owner wallet keeps full control and can revoke the key.
  • Portable. The key is independent of the wallet, so it can be moved to another device, such as a phone, which can then trade without the wallet app.
  • Verifiable by services. A delegation is public on-chain state, so an off-chain service can confirm that a request signed by the key comes from the account’s authorized key.

Creating and storing the key

Generate the key from fresh randomness in the client. Do not derive it from the owner’s address or from a wallet signature: a derived key needs an extra prompt, and anyone who can reproduce the derivation holds the key. The owner address only labels which owner a stored key belongs to. 

import { Wallet } from "ethers"

const sessionKey = Wallet.createRandom() // random; its address goes into the grant

A generated key has no authority until the owner grants it. The front end can create or restore the key early, and treat trading as enabled only once the delegation is active on-chain.

  • Encrypt it at rest. For example, encrypt the private key with AES-GCM under a non-extractable Web Crypto key kept in IndexedDB, and store only the ciphertext, the key’s address, and the owner it belongs to.
  • Scope storage to the deployment. Include the chain and the contract addresses in the storage key, so a key authorized on one deployment is never reused on another with different contracts on the same chain.
  • One key, several accounts. A single key can serve several SubAccounts of the same owner, but each SubAccount needs its own grant, and each grant is checked separately.
  • Losing storage means a new key. A lost key cannot be recreated. The front end generates a new one, and the owner authorizes its new address.

Authorizing the key

The owner authorizes the key by signing a delegation grant: a SignedOperation that targets InstantLayer with grantDelegation(DelegationInfo). It can travel in the same relayed batch as the key’s first operations, because InstantLayer applies the grant before it verifies the next operation. See Batch Delegation Grant Operations for the operation format and its rules. 

const grant = {
  account: { addr: subAccount, isPartyB: false }, // the account the key will act for
  delegatedSigner: sessionKey.address,
  selectors: [sendQuoteSelector, requestToClosePositionSelector, approveOperationalFeeSelector],
  expiryTimestamp: now + 7n * 24n * 3600n, // authority ends after one week
}
const grantCallData = instantLayer.interface.encodeFunctionData("grantDelegation", [grant])
// Wrap grantCallData in a SignedOperation targeting InstantLayer, signed by the owner.
  • Grant only what is missing. Read the current delegations first, and include the functions that are not active or expire soon.
  • Sign the key’s operations first. The key’s signatures need no prompt, so prepare them before asking for the owner’s signature. A typical first batch is the grant followed by the key’s approveOperationalFee, which lets the relayer charge operational fees to the account.
  • Verify after the batch. Read the delegation again before reporting that trading is enabled.

The fee approval is a standing allowance, separate from the delegation. Approving a large amount once avoids a new approval every time it runs out; approving a small amount caps what the relayer can charge.

Signing operations

The key signs each operation as EIP-712 typed data with the SymmioInstantLayer domain, version 1, the chain ID, and InstantLayer as the verifying contract. The operation’s target can be a different contract, such as Core or AccountLayer: InstantLayer verifies the signature, then calls the target. 

import { hexlify, randomBytes } from "ethers"

const op = {
  signer: sessionKey.address,
  target: core, // the contract to call
  callData, // the function and its arguments
  signerAccount: { addr: subAccountOrVirtualAccount, isPartyB: false },
  flexFields: [],
  maxUses: 1,
  replayAttackHeader: { nonce: 0n, deadline, salt: hexlify(randomBytes(32)) },
}
const signature = await sessionKey.signTypedData(
  { name: "SymmioInstantLayer", version: "1", chainId, verifyingContract: instantLayer },
  signedOperationTypes,
  op,
)
  • Replay protection. Each operation can run at most maxUses times, counted per signed operation, so a random salt with maxUses = 1 makes it single-use. A nonzero nonce additionally forces order: it must equal nonces(account) + 1, and consecutive operations in a batch use consecutive values. A zero nonce leaves the operation unordered.
  • Deadlines. Use short deadlines, and give operations that belong together, such as adding margin and opening the position it funds, the same deadline so one cannot execute long after the other expired.
  • Enforcement happens at execution. Signing does not check the delegation. A key can sign anything; only granted, unexpired functions execute. Check the delegation before submitting to give the user a clear error.

What a key can and cannot do

InstantLayer enforces these limits on-chain, against the calldata that actually executes:

  • Only the granted functions. Each operation’s function selector must have an active delegation to the key. For AccountLayer timelock wrappers (executeTimelockOp), the check applies to the wrapped function.
  • Only the granted account family. A grant covers the named SubAccount and its Virtual Accounts. Other SubAccounts of the same owner are rejected with AccountOutOfScope. See Delegation Account Scope.
  • No new delegations. Only the owner can sign a grant. A key cannot extend or share its own authority.
  • No amount limits. A grant restricts the account, the functions, and the expiry, nothing else. Each operation carries its own amounts. A key granted withdrawal functions can withdraw, so grant those only if the front end lets the key sign withdrawals.
  • No PartyB accounts. PartyB accounts cannot grant delegations.
  • Billed to the account. Operations relayed through Gasless Layer are billed to the account. The key can cap each operation’s charge with a signed fee limit; see Signed fee limits.

GaslessWallet operations

To sign operations for the owner’s GaslessWallets, the key needs WALLET_EXECUTION_SENTINEL_SELECTOR plus the selector of every call inside the wallet operation. It cannot send native currency from a wallet. Wallet permissions are checked by selector, not by target contract or wallet ID, so a granted selector works through every wallet the owner has. With the sentinel and a general token selector such as ERC-20 transfer or approve, the key could move any wallet’s tokens. See GaslessWallet operations.

Service delegates

An automated service, such as a take-profit and stop-loss bot, gets its own delegate address with its own functions and expiry, usually fewer functions and a longer expiry than the session key. The session key then signs requests to the service off-chain, for example "close this position at this price", and the service later executes them on-chain with its own delegation. The service can confirm that a request came from the account’s key with isDelegationActive.

grantDelegations(DelegationInfo[]) authorizes the session key and the service with one owner signature, each entry with its own functions and expiry.

Expiry, renewal and revocation

Three separate clocks apply, and each can end use independently:

Clock Set by When it ends
Stored key The front end The key can no longer be loaded on that device
Delegation expiryTimestamp in the grant The key’s signatures stop executing
Operation deadline in each signed operation That one operation can no longer execute

The key itself never stops being able to sign; only its authority expires. To renew, the owner grants the same key again with a new expiry; a new key is not needed. A grant with an expiry in the past reverts with DelegationExpired.

To end a key early, call initiateRevokeDelegation(account, key, selectors). The owner, the key itself, or an address with REVOKER_ROLE may call it. It is a direct transaction, not a relayed operation, so the caller pays its network fee. The revocation takes effect after revocationCooldown, which defaults to 10 minutes and can be set between 5 minutes and 30 days. The key keeps its authority until then, and loses it at that moment even if nobody calls finalizeRevokeDelegation; anyone may call that afterwards to clear the record. A new grant for the same functions cancels a pending revocation.

Deleting a key locally is not revocation. Any other copy, for example on a linked phone, keeps its authority until the delegation expires or a revocation takes effect. Operations the key already signed also stay valid until their deadline. Revoke on-chain when a key may have leaked, and keep expiries short.

Using a key on another device

A front end can extend a session to a second device, such as a phone, in two ways:

  • Share the same key. Transfer the private key through an end-to-end encrypted handoff, for example HPKE with a pairing secret shown as a QR code. No new grant is needed, but both devices then share one authority, and ending access on one device requires revoking the key everywhere.
  • Give the device its own key. Generate a new key on the second device and have the owner authorize it. This costs one more owner signature, but each device can be revoked on its own.

Checking a key

isDelegationActive(account, key, selector) returns whether the key may sign that function for the account now, accounting for expiry and any revocation that has taken effect. Pass the SubAccount address; delegations granted for a Virtual Account are recorded under its parent. delegations(account, key, selector) returns the expiry, which shows when to renew. getActiveDelegations lists active permissions for several keys at once. 

const active = await instantLayer.isDelegationActive(subAccount, sessionKey.address, sendQuoteSelector)
const expiresAt = await instantLayer.delegations(subAccount, sessionKey.address, sendQuoteSelector)
if (!active) {
  // Expired or revoked: ask the owner to grant this key again.
}

Security boundaries

  • Encryption protects stored data, not the running app. The key is decrypted into memory to sign, so any script running in the same origin can use it. It is not a hardware-wallet boundary.
  • The protocol, not the key, limits what executes. The key can sign any message. Only the delegation’s account, functions, and expiry decide what InstantLayer executes.
  • Grant the minimum. Give each key and service only the functions it uses, give onboarding-only permissions a short expiry in a separate grant entry, and never pair the wallet sentinel with general token selectors.
