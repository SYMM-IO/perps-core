v0.8.6/Liquidation

PartyA Liquidation Funding Snapshot Fix

This fix makes liquidation settlement use the same funding state that Muon signed when PartyA became liquidatable, so later PartyB funding updates cannot change the liquidation debt.

Summary

PartyA liquidation is supposed to settle from the accounting snapshot that made PartyA liquidatable. That snapshot includes PartyA UPNL, liquidation prices, and the funding debt implied by those prices and funding accumulators.

Before this fix, the legacy liquidation path froze symbol prices from the Muon liquidation signature, but accumulated funding could still be derived from funding storage later, when liquidatePositionsPartyA was called. If PartyB changed funding after PartyA was marked liquidated, settlement could use the liquidation price from one moment and funding state from another.

The fix adds a Muon-signed snapshot path. Muon now signs PartyA historical insolvency data plus the price and cumulative funding values needed for each (PartyB, symbolId) pair. Once the snapshot path is used for a liquidation, every liquidated quote must have a matching signed snapshot. If accumulated funding was not active for a pair at the liquidation timestamp, Muon should still include that pair with the liquidation price and zero cumulative long/short funding values. Missing snapshot coverage reverts instead of falling back to live funding.

Affected Scenario

The risky flow was:

  1. PartyA becomes liquidatable.
  2. Liquidator calls liquidatePartyA(partyA, liquidationSig).
  3. Liquidator calls setSymbolsPrice(partyA, liquidationSig).
  4. PartyB updates funding for one of PartyA's markets.
  5. Liquidator later calls liquidatePositionsPartyA(partyA, quoteIds).
  6. Settlement is calculated with frozen liquidation prices, but funding may come from the later funding state.

This could happen naturally, not only through a malicious timing attempt. Some solvers update funding frequently and may batch setFundingFee with open/close operations in the Instant Layer. If PartyA is marked liquidated between those solver operations and the later liquidation-close transaction, the liquidation path must not let the later funding update change PartyA's liquidation debt.

Why The Old Timestamp Fix Was Not Enough

A previous mitigation aligned liquidation funding calculations to the liquidation timestamp by using getAccumulatedFundingFeeAt(quoteId, liquidationTimestamp). That helps when the chain can still reconstruct the old funding accumulator from current storage.

The remaining problem is that current storage does not keep a full history of replaced funding state. If PartyB changes the current long/short rate, or changes epoch duration, the contract may no longer have enough information to reconstruct exactly what Muon saw at the liquidation timestamp. Asking the contract to store every historical funding change would push extra storage writes into normal solver operations.

That tradeoff is especially bad for solvers that update funding often. The liquidation fix should not make every normal open, close, or funding update more expensive.

Impact

The issue could affect liquidation accounting whenever funding changed between the liquidation snapshot and position liquidation.

Possible outcomes:

  • PartyA liquidation could dispute because partyAAccumulatedUpnl no longer matched the signed liquidation UPNL.
  • PartyA-level totals could appear close enough while value still shifted between PartyBs.
  • Liquidation debt could depend on keeper timing around funding updates.
  • Funding updates after liquidation could affect a debt value that should have been fixed at the liquidation snapshot.

The root invariant is simple: once PartyA is proven liquidatable at timestamp T, later PartyB funding changes must not change the liquidation settlement for timestamp T.

New Muon Payload

The snapshot path uses LiquidationSnapshotSig:

struct LiquidationPartyBSymbolState {
    address partyB;
    uint256 symbolId;
    uint256 price;
    int256 cumulativeLongFee;
    int256 cumulativeShortFee;
}

struct LiquidationSnapshotSig {
    bytes reqId;
    uint256 timestamp;
    bytes liquidationId;
    int256 upnl;
    int256 totalUnrealizedLoss;
    LiquidationPartyBSymbolState[] states;
    uint256 liquidationBlockNumber;
    uint256 liquidationTimestamp;
    uint256 liquidationAllocatedBalance;
    bytes gatewaySignature;
    IMuonSignatureVerifier.SchnorrSign sigs;
}

Each states entry freezes one PartyB-symbol pair:

  • partyB: the solver side of the position.
  • symbolId: the market.
  • price: liquidation price for that PartyB-symbol pair.
  • cumulativeLongFee: cumulative long funding value at the liquidation timestamp.
  • cumulativeShortFee: cumulative short funding value at the liquidation timestamp.

Snapshot liquidation always uses signed historical insolvency fields. liquidationBlockNumber, liquidationTimestamp, and liquidationAllocatedBalance must be nonzero and signed by Muon.

There is no live/deferred selector in this payload. Snapshot setup always supplies the signed historical timestamp and allocated balance to the shared PartyA liquidation start helper; the legacy live path uses that same helper with current values after performing its live-only expiry and open-position checks.

Muon signs the same core liquidation fields as before, plus the hash of states and the historical insolvency fields. The signature is verified through verifyLiquidationSnapshotSig, so a legacy liquidation signature cannot be reused as a snapshot signature.

What Changed On-Chain

The fix adds two storage concepts to AccountStorage:

mapping(address => mapping(bytes32 => bool)) liquidationUsesPartyBSymbolSnapshots;
mapping(address => mapping(bytes32 => mapping(address => mapping(uint256 => LiquidationPartyBSymbolSnapshot)))) liquidationPartyBSymbolSnapshots;

The first mapping is the snapshot marker. It says that a PartyA liquidation uses signed PartyB-symbol snapshots.

The second mapping stores the actual snapshot for:

partyA -> liquidationSnapshotKey -> partyB -> symbolId

The stored snapshot contains:

struct LiquidationPartyBSymbolSnapshot {
    bool isSet;
    uint256 price;
    int256 cumulativeLongFee;
    int256 cumulativeShortFee;
}

The liquidationSnapshotKey is computed from the active liquidation id, liquidation timestamp, and PartyA nonce. This avoids storing the same timestamp and liquidation id inside every individual snapshot.

The external API for this path lives on the separate PartyALiquidationSnapshotFacet:

liquidatePartyAWithSnapshot(address partyA, LiquidationSnapshotSig liquidationSig)
singleStepLiquidatePartyAWithSnapshot(address partyA, LiquidationSnapshotSig liquidationSig, uint256[] quoteIds)

The snapshot facet emits SetPartyALiquidationSnapshot with partyBs, symbolIds, prices, and cumulative funding arrays. It also emits the legacy SetSymbolsPrices event for compatibility with existing liquidation indexers.

Settlement Behavior After The Fix

When liquidatePositionsPartyA processes a quote, it checks whether the active liquidation uses signed PartyB-symbol snapshots.

If snapshot-backed pricing is active:

  • the quote must have a snapshot for (quote.partyB, quote.symbolId);
  • the close price comes from that snapshot;
  • accumulated funding is calculated from the signed cumulative long/short values;
  • pairs without accumulated funding active at the liquidation timestamp are represented by zero cumulative values; and
  • missing state reverts with LiquidationFacet: Missing signed state.

If snapshot-backed pricing is not active:

  • the legacy path remains unchanged;
  • price comes from setSymbolsPrice; and
  • funding is calculated with getAccumulatedFundingFeeAt(quote.id, liquidationDetail.timestamp).

Snapshot-backed pricing is all-or-nothing for an active liquidation. Once the snapshot marker is set, the liquidation cannot silently mix signed funding for some quotes with legacy funding for others.

Why We Did Not Store Funding History

An on-chain funding-history fix would require normal solver operations to write additional history whenever funding changes or when open/close logic moves accumulated funding state. That would make the common path more expensive for every market, even though liquidation is the uncommon path.

The snapshot design moves the cost to liquidation:

  • normal setFundingFee, open, close, and accumulated funding charge flows do not write liquidation history;
  • liquidators write only the PartyB-symbol states needed for the liquidation they are processing;
  • large PartyA accounts still use explicit quoteIds batching and never require iterating every PartyA position on-chain; and
  • deployments can keep the legacy path during migration, then disable it with a feature flag.

Legacy Deprecation Flag

Governance can require the new snapshot flow by calling:

setLegacyPartyALiquidationDeprecated(true)

When enabled, these legacy start entrypoints revert with LiquidationFacet: Legacy liquidation deprecated:

  • liquidatePartyA
  • deferredLiquidatePartyA

The flag does not block liquidatePartyAWithSnapshot, singleStepLiquidatePartyAWithSnapshot, pending-position liquidation, open-position liquidation, settlement, or dispute resolution. Existing legacy liquidations that already started can still set prices through setSymbolsPrice or deferredSetSymbolsPrice, then continue through liquidatePositionsPartyA and settlePartyALiquidation.

Expected Result

After this fix, PartyB can update funding after PartyA is marked liquidated, but that update does not change snapshot-backed liquidation settlement for the already captured liquidation timestamp.

The expected behavior is:

  • PartyA debt is fixed to the Muon-signed liquidation snapshot.
  • Later funding changes are ignored for that snapshot-backed liquidation.
  • Missing PartyB-symbol coverage fails explicitly.
  • Large liquidations remain batchable.
  • Normal solver funding updates do not become more expensive just to support historical liquidation reads.

Related Snapshot Entrypoints

liquidatePartyAWithSnapshot is the staged starter for this payload. singleStepLiquidatePartyAWithSnapshot is the full single-transaction path for accounts that can be closed and settled immediately. Both are documented separately in PartyA Liquidation Snapshot Entrypoints.
