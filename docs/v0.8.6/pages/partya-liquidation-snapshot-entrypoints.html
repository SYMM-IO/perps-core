v0.8.6/Liquidation

PartyA Liquidation Snapshot Entrypoints

The snapshot facet is the explicit PartyA liquidation path for Muon-signed price, funding, and historical insolvency state. It supports both staged liquidation and full single-transaction completion.

Summary

v0.8.6 adds a dedicated PartyALiquidationSnapshotFacet for PartyA liquidations that use a full Muon-signed snapshot. The snapshot includes PartyA historical insolvency data and the per-(PartyB, symbolId) price/funding states used later by liquidation settlement.

This is not a new liquidation type. The protocol still uses the existing NORMAL, LATE, and OVERDUE liquidation semantics. The change is the entrypoint and signature model: liquidators now submit one signed snapshot payload instead of combining a legacy liquidation signature with a separate price-setting step.

Facet And Entrypoints

The new external interface is:

interface IPartyALiquidationSnapshotFacet {
    function liquidatePartyAWithSnapshot(
        address partyA,
        LiquidationSnapshotSig memory liquidationSig
    ) external;

    function singleStepLiquidatePartyAWithSnapshot(
        address partyA,
        LiquidationSnapshotSig memory liquidationSig,
        uint256[] memory quoteIds
    ) external;
}

Both functions live on PartyALiquidationSnapshotFacet and require LIQUIDATOR_ROLE. The facet is separate from the legacy PartyALiquidationFacet, which keeps the new integration surface easy to remove or evolve independently after the old entrypoints are fully deprecated.

Snapshot calls keep emitting the legacy SetSymbolsPrices event for compatibility. They also emit SetPartyALiquidationSnapshot, which includes the PartyB dimension and cumulative funding fields needed to reconstruct the signed snapshot exactly.

Entrypoint Use
liquidatePartyAWithSnapshot Starts a snapshot-backed PartyA liquidation and stores the signed PartyB-symbol states. The liquidator then continues through the existing pending-position, open-position, and settlement functions.
singleStepLiquidatePartyAWithSnapshot Starts the snapshot liquidation, handles pending quotes, liquidates the provided open positions, derives the PartyBs from those quotes, settles, and reverts unless the liquidation fully completes.

Signed Snapshot Payload

The snapshot path uses LiquidationSnapshotSig:

struct LiquidationPartyBSymbolState {
    address partyB;
    uint256 symbolId;
    uint256 price;
    int256 cumulativeLongFee;
    int256 cumulativeShortFee;
}

struct LiquidationSnapshotSig {
    bytes reqId;
    uint256 timestamp;
    bytes liquidationId;
    int256 upnl;
    int256 totalUnrealizedLoss;
    LiquidationPartyBSymbolState[] states;
    uint256 liquidationBlockNumber;
    uint256 liquidationTimestamp;
    uint256 liquidationAllocatedBalance;
    bytes gatewaySignature;
    IMuonSignatureVerifier.SchnorrSign sigs;
}

Muon signs the PartyA historical insolvency fields, the hash of states, the deployment address, chain id, PartyA nonce, and the liquidation id. Snapshot liquidation always follows the historical insolvency path.

The snapshot payload does not include a live/deferred selector. The three historical fields below are always required, and the snapshot setup library passes them into LibPartyALiquidationShared.startPartyALiquidation. Legacy live liquidation reaches the same shared helper by passing current timestamp and current allocated balance instead.

Historical Proof

Field Field rules
liquidationBlockNumber Must be nonzero and signed by Muon.
liquidationTimestamp Must be nonzero and match the stored liquidation timestamp.
liquidationAllocatedBalance Must be nonzero and is the allocated balance used for the historical insolvency check.

If the account has current excess balance when the historical proof is used, that excess is moved to partyADeferredBalance before liquidation starts.

Staged Flow

Use the staged flow when PartyA has many positions, the liquidation needs batching, or settlement has to be split by PartyB: 

liquidatePartyAWithSnapshot
liquidatePendingPositionsPartyA
liquidatePositionsPartyA
settlePartyALiquidation

liquidatePartyAWithSnapshot marks PartyA as liquidated and stores the signed PartyB-symbol snapshots. The later liquidation functions use those stored snapshots for close price and accumulated funding calculations.

Single-Step Flow

singleStepLiquidatePartyAWithSnapshot is the one-transaction path for accounts that can be fully closed and settled in one call: 

singleStepLiquidatePartyAWithSnapshot(
    partyA,
    liquidationSnapshotSig,
    quoteIds
)

The function performs these steps in order:

  1. Verifies the Muon snapshot signature.
  2. Starts the PartyA liquidation using the signed historical insolvency fields.
  3. Stores every signed PartyB-symbol snapshot.
  4. Liquidates PartyA's pending quotes.
  5. Liquidates the provided open quoteIds.
  6. Derives the PartyB settlement list from quoteIds.
  7. Settles PartyA liquidation for those PartyBs.
  8. Reverts unless the liquidation is fully complete.

The single-step function has no liquidatePending flag because pending quotes are always handled. It also has no partyBs input because the settlement list is derived from the provided quotes.

Use the staged flow instead if the supplied quoteIds do not cover every open position and PartyB needed to finish settlement in the same transaction.

Snapshot Coverage Rules

For every quote liquidated under the snapshot-backed path, the contract looks up:

snapshot[partyA][liquidationSnapshotKey][quote.partyB][quote.symbolId]

If that snapshot is not set, liquidatePositionsPartyA reverts with:

LiquidationFacet: Missing signed state

Multiple quotes with the same PartyB and symbol share one snapshot. If the same symbol appears under different PartyBs, each PartyB needs its own snapshot. If accumulated funding was not active for one of those pairs at the liquidation timestamp, Muon should still include the pair with zero cumulative long/short funding values. The contract does not enforce same-symbol price equality across PartyBs.

Legacy Deprecation Relationship

setLegacyPartyALiquidationDeprecated(true) disables new legacy liquidation starts:

  • liquidatePartyA
  • deferredLiquidatePartyA

The flag does not disable liquidatePartyAWithSnapshot or singleStepLiquidatePartyAWithSnapshot. Existing legacy liquidations that already started can still call setSymbolsPrice or deferredSetSymbolsPrice, then continue through pending-position liquidation, open-position liquidation, settlement, and dispute resolution. This avoids stranding a PartyA between the legacy start and price-setting steps during migration.

Operator Checklist

Before submitting a snapshot liquidation, confirm:

  • the Muon payload is LiquidationSnapshotSig;
  • liquidationBlockNumber, liquidationTimestamp, and liquidationAllocatedBalance are present, nonzero, and signed by Muon;
  • states covers every (PartyB, symbolId) pair needed by the quotes to close;
  • quoteIds is small enough for one transaction when using the single-step entrypoint;
  • single-step usage can fully finish liquidation and settlement; and
  • large accounts use the staged flow instead of forcing all work into one transaction.
