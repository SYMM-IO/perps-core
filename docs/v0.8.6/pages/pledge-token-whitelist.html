Pledge Token Whitelist

v0.8.6 restricts new pledge deposits to explicitly approved tokens and gives token approval its own manager role.

Changes from v0.8.5

The v0.8.5 pledge lifecycle already supports deposits, withdrawal requests, approval, cancellation, and slashing. v0.8.6 adds a token whitelist to the deposit path.

Behavior v0.8.5 v0.8.6
Deposit admission No token whitelist check before the ERC20 transfer. depositPledge(token, amount) rejects an unapproved token before calling it.
Initial token policy No token approval step. Every token starts disabled, including the trading collateral. Each address needs explicit approval.
Token management No whitelist setter, getter, event, or dedicated role. PLEDGE_TOKEN_MANAGER_ROLE controls token approval and removal.

A deposit into an unapproved token reverts with PledgeFacet: Token is not whitelisted. Setting the protocol’s trading collateral does not add that token to the pledge whitelist.

New API and role

The Core diamond exposes two new functions and one event through PledgeFacet:

function setPledgeTokenWhitelist(address token, bool whitelisted) external;
function isPledgeTokenWhitelisted(address token) external view returns (bool);
event PledgeTokenWhitelistUpdated(address indexed token, bool whitelisted);

The setter requires PLEDGE_TOKEN_MANAGER_ROLE; the getter is public. The setter rejects the zero address, and enabling a token requires deployed code. It emits PledgeTokenWhitelistUpdated on every successful call and remains callable while accounting is paused. The existing role check also rejects calls with a configured signer context.

PARTY_B_MANAGER_ROLE does not authorize whitelist updates. It retains pledge withdrawal approval and slashing. Granting the new role gives an operator no withdrawal or slashing authority.

Token approval is a compatibility decision: deposits still credit the requested amount in native token units. The whitelist adds no balance-delta, transfer-fee, or rebase adjustment. Managers must review those token behaviors before approval.

Token removal

Calling setPledgeTokenWhitelist(token, false) stops new deposits of that token. Existing balances and withdrawal requests remain intact; removal adds no restriction to withdrawal requests, cancellation, approval, or slashing. Re-enabling the token permits new deposits again.

Upgrade impact

PledgeStorage.whitelistedTokens is appended after the existing balance and withdrawal-request mappings, preserving their storage slots. Existing tokens are not automatically approved after the upgrade.

  1. Add the two new selectors and replace the existing PledgeFacet selectors with the updated facet. Integrations must use the updated ABI to manage or read the whitelist; the depositPledge signature is unchanged.
  2. Explicitly grant keccak256("PLEDGE_TOKEN_MANAGER_ROLE") to the intended operator through an authorized role administrator. Existing PARTY_B_MANAGER_ROLE grants do not carry over. Fresh system deployments include the new role in the protocol-admin role manifest.
  3. Approve every reviewed token through the Core diamond and verify its status before resuming deposits. When the upgrade authority also holds the new role, token approvals can follow the cut in the same authorized batch. Otherwise, coordinate the cut and operator approvals while accounting is paused.
