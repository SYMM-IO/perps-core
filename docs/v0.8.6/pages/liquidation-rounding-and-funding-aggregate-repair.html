Liquidation Rounding and Funding Aggregate Repair

v0.8.6 separates harmless integer rounding from a real liquidation mismatch and keeps stored funding totals equal to the sum of their open quotes.

Summary

Muon calculates one total from position groups. Liquidation settles the same account quote by quote. Integer division can make those two correct paths differ by a few raw accounting units. The contract records how many positions existed when liquidation started and accepts up to three raw accounting units per starting position.

The allowance is fixed at 3 raw units per starting position and always applies. A larger mismatch still opens a dispute.

When the difference is inside the limit, settlement uses the smaller same-direction amount supported by both Muon and the quote calculation. If they disagree about which side won, the rounded payment is zero. The removed part is never written to a balance or separate accounting field.

Rollout prerequisites. The bound assumes repaired funding aggregates and exact aggregate notional in Muon. Complete both while affected actions are paused, before resuming with the fixed allowance.

Why liquidation totals can differ

Consider two values with decimals that the contract cannot store:

Quote-by-quote: cut(4.8) + cut(5.8) = 4 + 5 = 9
Group total:    cut(4.8 + 5.8)        = cut(10.6) = 10

Neither answer means the price or funding data is false. The difference comes from where the decimal part is removed. Price PnL can lose less than one unit per quote, and funding can lose less than two. This gives a maximum of three raw units for each position, provided the stored totals and Muon inputs are exact.

The position count is saved at liquidation start, so closing positions in several batches cannot shrink or grow the limit. The final settlement amount is the smaller magnitude when both calculations agree on its direction. For example, losses of 100 and 101 settle at 100. No rounding residual is stored or assigned to another account.

Why partial closes left dust

A funding group stores the sum of each open quote's rounded contribution. The old close path rounded the closed slice on its own. Because rounding does not always split cleanly, a 60% close followed by a 40% close could leave one raw unit after the position reached zero. 

Old behavior: remove cut(closed amount × funding)
New behavior: remove cut(old open amount × funding)
                   − cut(new open amount × funding)

The new calculation makes the stored value exactly match the remaining quote after every partial close. When the last position in a pair or global PartyB group closes, its funding total is also set to zero. Reopening the same group then starts without old dust.

Exact Muon PnL input

The original UPNL views return an average open price. Dividing notional by amount to make that average can drop a remainder. Multiplying the rounded average by the amount later cannot restore it. 

Old LONG price PnL: (price − rounded average) × amount / 1e18
New LONG price PnL: (price × amount − exact notional) / 1e18

The new getPartyAExactNotionalUpnlData, getPartyBExactNotionalUpnlData, and getPartyBGlobalExactNotionalUpnlData views return the stored aggregatedNotional. The old views remain unchanged for existing readers. The corresponding Muon implementation must enable the exact-notional path for contract addresses listed in MUON_EXACT_NOTIONAL_CONTRACTS.

Muon must calculate each funded group once. That same result is added to total UPNL and, when negative, to total unrealized loss. This prevents the two signed fields from disagreeing because they rounded the same group in different ways.

OVERDUE safety. A rounding-sized mismatch can make a calculated loss reduction one unit larger than a quote's loss. The reduction is now capped at that quote's loss, so the liquidation reaches the normal dispute check instead of reverting.

Repairing existing groups

The one-time repair calculates the correct quote-level totals off chain. This avoids an unbounded on-chain loop when one PartyA and PartyB pair has many open quotes. scripts/resyncAggregateFunding.ts reads the pair in real pages at one fixed, globally paused block and calculates each quote independently: 

open amount = quantity − closed amount
quote contribution = (open amount × accumulated paid funding) / 1e18
new group funding = sum of the rounded quote contributions

The script uses checked BigInt arithmetic with Solidity's signed division rule, including truncation toward zero. It therefore preserves raw-unit differences. The paginated quote getter reads only the requested page instead of copying the pair's full open-position list first. The script reads until the array ends and verifies that the number of returned quotes matches partyBPositionsCount before producing calldata.

resyncAggregateFunding receives each final value together with the exact PartyA and PartyB pair values observed by the script. The contract requires a global pause, rejects liquidating parties, and reverts if either observed value has changed. It then sets both pair values to the calculated value and changes the global PartyB value by only that pair's correction: 

new global PartyB funding = old global funding − old pair funding + new pair funding

Groups are applied atomically in input order. An empty batch does nothing, and repeating a completed repair is a no-op. A real change raises both UPNL counters so old Muon signatures become invalid. AggregateFundingResynced records the old and new values for every input group. The contract trusts MIGRATION_ROLE to submit the script-reviewed final value; it does not scan quotes during the transaction.

The groups file is a JSON array. Use decimal strings for symbol IDs so JSON cannot round a large integer.

[
  {
    "partyA": "0x...",
    "partyB": "0x...",
    "symbolId": "1",
    "positionType": "LONG"
  }
]
GROUPS_FILE=./groups.json SYMMIO=0x... \
npx hardhat run --no-compile scripts/resyncAggregateFunding.ts --network <network>

The default run is read-only and prints exact calldata for governance review. Set OUTPUT_FILE to save that plan. To send it with the configured MIGRATION_ROLE signer, add EXECUTE=true and CONFIRM_CHAIN_ID=<chain-id>. PAGE_SIZE controls RPC page size and GROUP_BATCH_SIZE controls the number of constant-gas repairs in each transaction.

Safe rollout

Treat this as an update to the target diamond's actual deployed state. Deployments already running the v0.8.6 rounding release have the three-unit allowance and liquidation-start position count; this update does not introduce or enable them.

The deployment scope includes MigrationFacet, ViewFacetAggregate, and ViewFacetQuote, plus the funding and liquidation changes in PartyBBatchActionsFacet, PartyBLiquidationFacet, PartyBPositionActionsFacetImpl, SymbolAdjustmentFacet, ClearingHouseFacetImpl, LibQuoteClose, LibForceActions, and LibPartyALiquidationProcess. Changes to internal funding helpers are compiled into their callers, so a source-file list alone is not a complete deployment list.

Build the final deployment list from the compiled bytecode and artifact linkReferences. If a linked library gets a new address, relink and redeploy every caller, including callers of those callers. This includes ClearingHouseFacet, ForceActionsFacet, ForceCloseStepsFacet, PartyAFacet, both PartyA liquidation facets, PartyBEmergencyActionsFacet, PartyBExecutionFacet, PartyBPositionActionsFacet, and PartyBQuoteActionsFacet. Deploy library dependencies before their callers, then update the diamond's facet mappings.

Check selectors before building the cut. Query facetAddress(bytes4) through the diamond loupe for each function signature. Use Add for an absent selector and Replace for an existing selector that must point to an updated facet. Only use Remove for a deployed selector that is intentionally retired. Removing an absent selector reverts the whole cut. The four-field repair variant was an intermediate development version; its presence in Git is not evidence that it was deployed. Do not include its removal unless the target loupe confirms it exists and the upgrade retires it.

The seven-field repair function has this canonical ABI signature; the position-type enum is encoded as uint8:

resyncAggregateFunding((address,address,uint256,uint8,int256,int256,int256)[])
  1. Record the target chain, diamond address, deployed facets, and library addresses. Prepare the complete deployment and selector plan above, then rehearse the upgrade and repair against a recent fork of that deployment.
  2. List the affected funding groups in the JSON input file and finish active PartyA and PartyB liquidations involving them before the global pause. The repair rejects liquidating parties, and a global pause also blocks liquidation settlement. If a liquidation cannot finish, resolve it through the existing dispute or Clearing House flow before repairing its groups.
  3. Globally pause the protocol and confirm that the affected accounts are no longer liquidating. Deploy the updated libraries and dependent facets, refresh the target's selector inventory, and apply the reviewed diamond cut. Verify its facet mappings, the seven-field repair selector, and the exact-notional getters before calculating repairs.
  4. Run scripts/resyncAggregateFunding.ts without EXECUTE. Review the fixed block, every old and new raw value, and the generated calldata. Keep the global pause in place and avoid other state-changing migrations throughout the calculation and repair.
  5. Execute the reviewed batches, then verify each event and the script's pair and global post-checks before unpausing.
  6. Activate the corresponding Muon implementation, add the deployed chain and diamond address to MUON_EXACT_NOTIONAL_CONTRACTS, then restart Muon.
  7. Verify repaired funding totals and exact-notional Muon calculations, then resume affected actions.

When the fixed allowance accepts a difference, both parties settle using the smaller same-direction amount. The discarded difference is not a payment and is not stored, emitted, or assigned to a vault or account.
