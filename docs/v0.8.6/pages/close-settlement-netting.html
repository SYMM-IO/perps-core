Close Settlement Netting

Before v0.8.6, a close moved funding and realized PnL one after the other. That could reject a valid close. The new flow calculates both amounts first, checks only what remains, and then moves the balances.

Before v0.8.6

When a quote closed, the contract handled accumulated funding and realized PnL as two separate payments. It always moved funding first and PnL second.

  1. Calculate accumulated funding, check the payer's balance, and transfer the funding payment.
  2. Calculate realized PnL, check the payer's balance again, and transfer the PnL payment.
  3. Charge PartyA's platform close fee, update the quote, and run the hooks.

Each payment had to pass its balance check at that exact point in the sequence.

The problem

Funding and PnL can move in opposite directions. The first payment could fail even when the second payment would more than cover it. Reversing the order would not solve the problem; it would only make the opposite case fail first.

The 70 / 80 / 90 case

Suppose PartyB begins with 70 allocated, owes PartyA 80 in funding, and is owed 90 because PartyA realizes a loss on the close. From PartyA's perspective: 

funding receipt    +80
realized PnL       -90
----------------------
net to PartyA      -10

The old flow tried to take 80 from PartyB's balance of 70 and stopped there. It never applied the 90 credit. The correct result is simple: PartyA pays 10, and PartyB finishes with 80. The platform close fee is checked separately later.

How v0.8.6 fixes it

The contract now calculates funding and PnL before it moves either balance. It then asks one question: after both amounts are applied, which party still owes money, and how much?

The calculation is written from PartyA's point of view. A positive fundingFee means PartyA pays PartyB. A negative fundingFee means PartyA receives funding from PartyB. 

partyAReceives =
    (PartyA profit ? pnl : 0)
  + (fundingFee < 0 ? abs(fundingFee) : 0)

partyAPays =
    (PartyA loss ? pnl : 0)
  + (fundingFee > 0 ? fundingFee : 0)

netToPartyA = partyAReceives - partyAPays
  • If netToPartyA > 0, PartyB must have enough in the allocation used by the quote. Cross mode uses PartyB's shared allocation; isolated mode uses the allocation for this PartyA.
  • If netToPartyA < 0, PartyA's allocated balance must cover its absolute value.
  • If the totals are equal, neither party owes anything for funding and PnL.

After this check, the contract adds every funding and PnL credit before it subtracts any debit. A valid close can no longer fail simply because a debit came before the credit that covers it.

The transaction is all-or-nothing. If a later debit, fee, state update, or hook fails, the earlier credits and every other change are reverted.

How a close is processed

Single-quote and batch closes follow the same order:

  1. Calculate each quote. Validate the fill, release its share of the locks, record accumulated funding, and calculate realized PnL.
  2. Check the totals. Add everything PartyA receives and everything PartyA pays. Check the balance of the party that owes the difference.
  3. Move balances. Apply every credit first, then apply every debit.
  4. Update the quotes. Emit QuoteFundingSettled when accumulated funding is enabled, charge PartyA's close fee, update closed amounts and average prices, reduce aggregate positions, set quote statuses, and update party connections.
  5. Notify external consumers. Run the close and fee hooks, record trade volume, and emit the fill events.

For a batch, the contract completes each step for every quote before moving to the next step. It calculates all quotes before checking balances, applies all credits before any debit, and updates all quotes before the first hook runs. Every quote in the batch must belong to the same PartyA and PartyB.

Batch safety

Each quote ID may appear once

The contract reduces a quote's locks before it updates closedAmount. If the same quote appeared twice—for example, as 40% and 60% fills—the second entry could use the old open amount after the first entry had already reduced the locks. The quote could close with collateral still locked.

To prevent this, the contract checks for repeated quote IDs before it changes any state. A repeated ID reverts with LibQuoteClose: Duplicate quoteId. The same quote can still be filled more than once through separate transactions.

Quote order does not change the balance check

For valid, unique quote IDs, changing the order does not change the funding and PnL totals or the final allocated balances. It does change the order of events and hooks. A hook can revert the transaction, so this guarantee does not cover hook behavior.

Accumulated-funding batches use the same order. The contract records funding for every quote, applies all credits, and then applies all debits. The existing signed UPNL solvency check still runs separately.

Events and hooks

Combining funding and PnL for the balance check does not combine their records. Indexers still receive BalanceChangePartyA and BalanceChangePartyB events. The event's _type field identifies the change as FUNDING_FEE_IN, FUNDING_FEE_OUT, REALIZED_PNL_IN, or REALIZED_PNL_OUT. Each quote with accumulated funding enabled also reports its funding amount through QuoteFundingSettled.

Batch events appear in this order:

  1. All non-zero funding and PnL credits, in quote input order.
  2. All non-zero funding and PnL debits, in quote input order.
  3. Each quote's final events, including QuoteFundingSettled when accumulated funding is enabled, any non-zero PLATFORM_FEE_OUT balance change, and TradingFeeCharged(CLOSE).
  4. Affiliate and system callbacks, followed by TradeVolumeRecorded(CLOSE), for each quote.
  5. Both FillCloseRequest event forms for each quote, carrying final status and close ID; the extended form also includes the final locked values.

No close hook runs until every quote in the batch has its final balances, fees, locks, closed amount, aggregate position, and status. For each quote, callbacks run in this order: affiliate onClosePosition, affiliate onFeeCharged(CLOSE), system onClosePosition, then system onFeeCharged(CLOSE).

Hooks now see the whole completed batch. A hook that relied on earlier quotes being final while later quotes were still open must be updated. Before each hook call, the contract clears signer and InstantLayer privileges. If a hook fails, HookReverted reverts the entire close.

Fees and unchanged behavior

The platform close fee is checked separately

The net balance check covers only accumulated funding and realized PnL. It does not include PartyA's platform close fee. That fee is filledAmount * closedPrice * closeFee / 1e36 and is charged after the funding and PnL balances move. If PartyA cannot pay it, the whole transaction reverts.

What stays the same

Updates to accumulatedPaidFunding, Muon signature verification, signed UPNL solvency checks, and the close-fee formula work as before. Price and fill rules, partial closes, lock release, quote status changes, and connection cleanup are also unchanged.
