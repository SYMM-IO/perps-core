MARKET_BEST_EFFORT Close Orders

A one-shot close mode that fills the requested quantity when it is solvent, or fills the current liquidation-limited amount and atomically cancels the remainder.

Summary

v0.8.6 appends MARKET_BEST_EFFORT as OrderType value 2. It is valid only for close requests. LIMIT remains value 0, and MARKET remains value 1. Opening a quote with value 2 reverts, including openings routed through AccountLayer or InstantLayer.

PartyA submits the existing requestToClosePosition call with the requested quantity, price, deadline, and order type. No selector, storage field, event, or user-defined minimum-fill parameter was added.

Choose a close mode

Mode Ordinary fill Close-to-liquidation Unfilled request
LIMIT (0) Full or partial Supported Remains live
MARKET (1) Full only Rejected None after the full fill
MARKET_BEST_EFFORT (2) Full only while live Supported Cancelled after a partial liquidation-limited fill

Use LIMIT when the remainder should stay available for later fills. Use MARKET when PartyB must fill the live request completely through the ordinary fill path. Use MARKET_BEST_EFFORT when PartyA wants one execution attempt and accepts the protocol's current solvency-limited quantity.

Execution lifecycle

  1. PartyA creates a value-2 close request. The quote enters CLOSE_PENDING.
  2. PartyB submits either the legacy or fee-aware fillCloseRequestToLiquidation transaction. The contract validates the request and calculates the maximum amount that can close at the liquidation edge.
  3. If the full requested amount is executable, the contract fills it. The quote becomes CLOSED only when no position remains; otherwise it returns to OPENED with the close request cleared.
  4. If only part of the request is executable, the contract moves the quote to CANCEL_CLOSE_PENDING immediately before filling. The existing close finalizer fills that amount once, clears quantityToClose and requestedClosePrice, and returns the quote to OPENED.
Ordinary full fills remain available. While the request is in CLOSE_PENDING, PartyB can call fillCloseRequest only with the complete quantityToClose. A PartyB-selected partial amount reverts.

Worked example: a 100-unit position

Assume PartyA requests a best-effort close for the entire remaining position of 100 units.

Fully solvent
requested              100
liquidation limit      100 or more
actual fill            100
cancelled remainder      0
final quote status     CLOSED

Liquidation-limited
requested              100
liquidation limit       62
actual fill             62
cancelled remainder     38
final quote status     OPENED

The second transaction does not leave a live 38-unit close request. PartyA still owns the remaining 38-unit position, but must create a fresh close request before PartyB can try again.

Manual cancellation

PartyA can call requestToCancelCloseRequest before PartyB executes the request. This moves the quote to CANCEL_CLOSE_PENDING. While cancellation is pending, PartyB may use the ordinary fillCloseRequest method with a smaller amount. The fill succeeds and the existing cancellation finalizer clears the remainder.

This preserves the existing cancellation race: PartyA has already asked to stop the request, so the remainder is cancelled even when PartyB fills only part of it. The full-only ordinary-fill rule applies while the request remains in CLOSE_PENDING.

Guardrails and rollback

Best effort has no user-configured minimum fill, but “best effort” does not mean every nonzero calculated amount succeeds. The existing protocol checks still apply:

  • the calculated executable amount must be greater than zero;
  • the remaining position must satisfy the symbol's minimum acceptable quote value;
  • each proportional locked-value slice used by the fill must remain nonzero;
  • the close price, deadline, Muon signature, and request state must be valid;
  • PartyA and PartyB must pass the existing post-close solvency checks; and
  • fee-aware execution must remain within the quote's close solver-fee rate cap.

A failure reverts the entire transaction. No partial position update, cancellation-state transition, or solver-fee charge remains after the revert.

Solver fees

The fee-aware close-to-liquidation method accepts maxQuantity and an absolute solverFee. For MARKET_BEST_EFFORT, maxQuantity must be at least the full requested quantity. PartyB cannot use the cap to choose a smaller fill; only the liquidation calculation may reduce the amount.

Because the cap cannot bind, LIMIT's filledAmount / uncappedAmount fee-proration branch does not apply. The supplied solver fee remains absolute against the liquidation-limited amount and is still checked against the quote's close solver-fee rate cap. See Solver Fees for the complete fee model.

Integration routes

  • Core. Encode OrderType value 2 in the existing requestToClosePosition call. Do not use value 2 in any quote-opening call.
  • AccountLayer. The enum mirror decodes value 2. A liquidation-limited partial close leaves the position open, so the virtual account continues tracking the quote.
  • InstantLayer. Existing signed close operations can forward value 2 without a selector or template change. Opening operations still reject it.
  • External clients. Append value 2 to local enum mirrors. Preserve the deployed meanings of values 0 and 1.

Events and bot behavior

  • Treat frontend previews and getMaxCloseAmountToLiquidation as estimates. The signed values and on-chain state can change before execution.
  • Read the actual fill amount, final quote status, and closeId from the transaction's FillCloseRequest event.
  • After a partial best-effort fill returns the quote to OPENED, stop retrying the completed request. Another fill against that request reverts.
  • If PartyA still wants to close the remaining position, create a new request and track its new closeId.

What stays unchanged

  • LIMIT retains persistent partial-fill behavior.
  • MARKET remains full-fill-only and is still rejected by close-to-liquidation execution.
  • Force close remains restricted to LIMIT requests.
  • No new external selector, storage field, or event was added.
  • Historical v0.8.5 documentation is unchanged.
