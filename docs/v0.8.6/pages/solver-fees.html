Solver Fees

A solver fee is now an explicit, fixed-amount charge against an OPEN or CLOSE budget. Trading actions stay fee-less, while an arbitrary tag chooses the PartyB-configured receiver.

Summary

v0.8.6 separates solver-fee collection from position execution. The fee-bearing overloads of openPosition, fillCloseRequest, and fillCloseRequestToLiquidation are removed, while lockAndOpenPosition returns to a fee-less signature. PartyB opens or closes through the ordinary trading entrypoints, then uses one standalone method when it needs to collect a fee: 

function chargeSolverFee(
    uint256 quoteId,
    SolverFeeType feeType, // OPEN or CLOSE
    uint256 amount,
    bytes calldata tag
) external;

The amount is debited from PartyA's allocated balance and credited to the receiver resolved for the supplied tag. The quote's user-approved OPEN or CLOSE rate cap still limits cumulative charges. Flat operational fees remain a separate allowance-based mechanism; see Operational Fees.

Quote-time consent

PartyA opts in by sending the quote with immutable rate caps. A zero cap disables that side. The existing quote state remains the source of truth for both the approved rates and amounts already charged: 

struct SolverFeeCaps {
    uint256 openRateCap;
    uint256 closeRateCap;
}

struct SolverFeeState {
    uint256 openRateCap;
    uint256 closeRateCap;
    uint256 openFeeCharged;
    uint256 closeFeeCharged;
}

Caps are 18-decimal ratios. Quote creation emits SendQuoteSolverFeeCaps when either cap is non-zero. Legacy quote methods store zero caps, so their quotes cannot be charged through this path. A partial open copies the two rates to the child quote; each quote then accounts for its own notional and cumulative charges.

Standalone charge API

Only the PartyB assigned to the quote may call chargeSolverFee. The amount must be positive, PartyB actions must be active, neither party may be in the relevant liquidation state, the quote may not be closed or liquidated, the selected side must have an eligible notional basis, and PartyA must have enough allocated balance for the exact amount. The PartyB open-position pause does not block this fee-only call.

OPEN becomes available after the quote has an initial opened price. CLOSE is available only while a close request is live, so PartyB collects that fee before filling the request. Once the position is fully closed, the normal lifecycle guard rejects further charges.

The tag is arbitrary bytes supplied by PartyB and is emitted in raw form. Core hashes it internally for receiver routing; indexers can derive the same value with keccak256(tag) when a fixed-width key is useful. Tags are not replay identifiers or authorization proofs. Reusing a tag is allowed. OPEN tags share the quote's cumulative cap; CLOSE tags share the cap usage of the current close request.

Notional and cap accounting

An OPEN charge uses the quote's full opened notional:

openNotional = quantity * initialOpenedPrice / 1e18
openFeeCharged + amount <= openNotional * openRateCap / 1e18

A CLOSE charge uses only the current pending request:

closeRequestNotional = quantityToClose * requestedClosePrice / 1e18
closeRequestFeeCharged[closeId] + amount
    <= closeRequestNotional * closeRateCap / 1e18

Already closed quantity contributes nothing to this calculation. Each close request has a unique closeId and its own cap usage, so a fee on an earlier request does not consume a later request's budget. The quote-level closeFeeCharged value remains a lifetime accounting total across those requests.

Solver fees do not participate in close-to-liquidation sizing. The planner and getMaxCloseAmountToLiquidation account for the position close and protocol close fee only. Charge any solver fee separately; it is neither prorated to the selected fill nor reserved by the planner.

Tagged receiver routing

Receiver resolution has three levels, evaluated at charge time:

  1. The receiver configured for keccak256(tag).
  2. The PartyB's default solver-fee receiver.
  3. The PartyB address itself.
function setSolverFeeReceiver(address partyB, address receiver) external;

function setSolverFeeReceiverForTag(
    address partyB,
    bytes calldata tag,
    address receiver
) external;

function getSolverFeeReceiver(address partyB) external view returns (address);

function getSolverFeeReceiverForTag(
    address partyB,
    bytes calldata tag
) external view returns (address);

The registered PartyB or PARTY_B_MANAGER_ROLE may set either receiver. Passing address(0) to the tag setter clears that override and restores fallback behavior. Changing a receiver only affects later charges. The resolved receiver cannot equal the quote's PartyA, because that would move allocated margin into PartyA's free balance without the normal deallocation cooldown.

Accounting and events

allocatedBalances[partyA] -= amount
balances[resolvedReceiver] += amount

PartyB margin is not changed. The debit emits BalanceChangePartyA with OPEN_SOLVER_FEE_OUT or CLOSE_SOLVER_FEE_OUT. Both sides share one indexed event: 

event SolverFeeCharged(
    uint256 indexed quoteId,
    address partyA,
    address indexed partyB,
    address receiver,
					uint256 symbolId,
					SolverFeeType feeType,
					uint256 amount,
					bytes tag
);

event SetSolverFeeReceiverForTag(
		address indexed partyB,
		address indexed receiver,
		bytes tag
);

Clearing House liquidation cannot charge a solver fee. Its position-liquidation method accepts only the subject, quote IDs, and liquidation prices. This matches PartyA liquidation, which does not pay PartyB a solver fee.

Integration order

  1. PartyA creates the quote with the OPEN and CLOSE rate caps it accepts.
  2. PartyB locks and opens through the ordinary entrypoints or the fee-less combined lockAndOpenPosition.
  3. PartyB calls chargeSolverFee(quoteId, OPEN, amount, tag) when an OPEN fee is due.
  4. For closing, PartyA creates the close request.
  5. PartyB calls chargeSolverFee(quoteId, CLOSE, amount, tag) against that request's pending notional.
  6. PartyB fills the close request.

The fee and trade are separate calls and therefore separate state transitions. A solver contract such as SymmioPartyB may place both calls, charge first and fill second, in one outer batch when atomic service behavior is desired. Core no longer exposes fee-bearing trading overloads. The same ordering works for a one-fill, POSITION-isolated AccountLayer close because the fee is collected before final-close cleanup removes the virtual account.

Safety boundary

chargeSolverFee does not accept or verify a Muon uPnL signature and does not run a post-fee solvency or liquidatability check. Its financial limits are the quote-time rate cap and PartyA's current allocated balance. A successful charge may leave PartyA liquidatable. Integrators must not treat a successful fee charge as proof that PartyA remains solvent.

The call also does not prove that an off-chain service associated with a tag occurred. PartyA's consent is the per-quote rate cap; PartyB controls when to charge, which tag to attach, and where each tag routes. Indexers should use quoteId, feeType, and the raw tag from the event for attribution without interpreting the tag as extra on-chain authorization. They may derive keccak256(tag) off-chain for indexed storage or joins.

Upgrade notes

  • Add chargeSolverFee(uint256,uint8,uint256,bytes) to PartyBExecutionFacet.
  • Keep only the five-argument, fee-less lockAndOpenPosition.
  • Remove the three fee-bearing open/close selectors and the six-argument combined-open selector.
  • Remove the closeSolverFees input from liquidatePositionsForClearingHouse.
  • Replace OpenSolverFeeCharged and CloseSolverFeeCharged consumers with SolverFeeCharged.
  • Update getMaxCloseAmountToLiquidation callers to the four-argument form without a solver fee.
  • The per-tag receiver mapping is appended to MAStorage.Layout; existing default receiver settings remain valid.
