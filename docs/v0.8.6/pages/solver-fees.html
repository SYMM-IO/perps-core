v0.8.6/Fees

Solver Fees

v0.8.6 adds explicit operational and solver fees, charged from PartyA allocated balance instead of being hidden inside a worse execution price.

Summary

v0.8.6 adds explicit solver-fee accounting for quote open and close flows. Instead of forcing solvers to recover every fee through execution-price spread, PartyA can approve capped fee budgets on the quote. PartyB can then charge operational fees against the quote-level cap and solver fees against the relevant open or close cap.

The charged amount is deducted from allocatedBalances[partyA] and credited to balances[partyB]. This keeps open and close prices cleaner while making solver revenue observable on-chain.

Why We Added This

The old solver compensation path was implicit: the solver could make the open or close price worse for the user and keep the difference as spread. That can produce confusing execution prices, especially in markets where a small absolute fee looks like a large price spread.

Solver fee caps move that compensation into a direct accounting path. The price can remain closer to the expected market execution, while the fee is tracked as a separate debit from PartyA allocated balance.

Fee Model

There are two fee buckets:

  • Operational fee: an absolute quote-level cap only. This is for fixed operational costs, such as a flat fee per position, and it is not tied to open or close notional.
  • Solver fee: a rate cap only. The rate cap is checked against quote notional.

Operational and solver fees are charged only through the fee-aware open or close execution helpers. Each helper call is valid as long as the cumulative charged amount remains inside the user's cap: 

chargedOperationalFee + newOperationalFee <= maxOperationalFee
chargedOpenSolverFee + newOpenSolverFee <= openNotional * maxOpenSolverFeeRate / 1e18
chargedCloseSolverFee + newCloseSolverFee <= closeNotional * maxCloseSolverFeeRate / 1e18

API Surface

The operational fee cap is stored once per quote. Solver fee rate caps are stored directly for the open and close sides. 

struct SolverFeeCaps {
    uint256 maxOperationalFee;
    uint256 maxOpenSolverFeeRate;
    uint256 maxCloseSolverFeeRate;
}

struct SolverFeeState {
    uint256 maxOperationalFee;
    uint256 maxOpenSolverFeeRate;
    uint256 maxCloseSolverFeeRate;
    uint256 chargedOperationalFee;
    uint256 chargedOpenSolverFee;
    uint256 chargedCloseSolverFee;
}

PartyA can create a quote with a quote-level operational fee cap and immutable open-side and close-side solver fee caps using the new sendQuote overload. PartyB sees both fee budgets before choosing whether to lock and open the quote. 

function sendQuote(
    address[] memory partyBsWhiteList,
    uint256 symbolId,
    PositionType positionType,
    OrderType orderType,
    uint256 price,
    uint256 quantity,
    uint256 cva,
    uint256 lf,
    uint256 partyAmm,
    uint256 partyBmm,
    uint256 deadline,
    address affiliate,
    SingleUpnlAndPriceSig memory upnlSig,
    bytes memory data,
    SolverFeeCaps memory solverFeeCaps
) external returns (uint256 quoteId);

The legacy sendQuoteWithAffiliate and sendQuoteWithAffiliateAndData methods remain available and keep their selectors. The legacy no-affiliate sendQuote selector is removed in v0.8.6 -- integrations that used it must migrate to one of the remaining methods. Legacy methods store zero solver fee caps, so PartyB cannot charge a solver fee unless the user used the capped quote API.

The existing SendQuote(address,uint256,address[],address,bytes,bytes) event keeps its original paramsData layout for backward compatibility. When a quote has non-zero caps, the protocol emits a separate SendQuoteSolverFeeCaps event with partyA, quoteId, maxOperationalFee, maxOpenSolverFeeRate, and maxCloseSolverFeeRate.

Close solver fee caps are fixed at quote creation. PartyA cannot lower or replace them in requestToClosePosition, which prevents a user from changing solver economics right before relying on force close.

PartyB configures its operational-fee receiver through ControlFacet:

// ControlFacet
function setOperationalFeeReceiver(address receiver) external;

By default, operational fees are credited to the PartyB's own free balance. Setting a non-zero receiver credits future operational fees to that account instead. Setting the receiver to address(0) resets the default. Operational fees and open/close solver fees are intentionally not exposed as standalone charge selectors; they are charged inside the matching execution transaction so the fee and the solvency check stay atomic.

For execution paths with solver fees, PartyB uses the fee-aware PartyBSolverFeeActionsFacet methods: 

function openPosition(
    uint256 quoteId,
    uint256 filledAmount,
    uint256 openedPrice,
    PairUpnlAndPriceSig memory upnlSig,
    uint256 operationalFee,
    uint256 solverFee
) external;

function fillCloseRequest(
    uint256 quoteId,
    uint256 filledAmount,
    uint256 closedPrice,
    PairUpnlAndPriceSig memory upnlSig,
    uint256 operationalFee,
    uint256 solverFee
) external;

function fillCloseRequestToLiquidation(
    uint256 quoteId,
    uint256 closedPrice,
    PairUpnlAndPriceSig memory upnlSig,
    uint256 operationalFee,
    uint256 solverFee
) external returns (uint256 filledAmount);

The legacy fillCloseRequestToLiquidation method remains available for backward compatibility, but it reserves room only for the protocol close fee. It does not reserve room for solver fees. Use the solver-aware version whenever a close-to-liquidation fill will include an operational or solver fee.

Integrators can read the stored caps, cumulative charges, and effective operational-fee receiver with:

function getSolverFeeState(uint256 quoteId) external view returns (SolverFeeState memory);

function getOperationalFeeReceiver(address partyB) external view returns (address);

Bots can also preview close-to-liquidation sizing before submitting the transaction. Pass the total operational plus solver fee as solverFeeAmount, or 0 for a fee-less close: 

function getMaxCloseAmountToLiquidation(
    uint256 quoteId,
    uint256 closedPrice,
    uint256 marketPrice,
    int256 upnlPartyA,
    uint256 solverFeeAmount
) external view returns (uint256 maxCloseAmount, bool canCloseAll);

Notional and Rate Caps

Open solver fee rate caps use the opened quote notional:

openNotional = quote.quantity * quote.initialOpenedPrice / 1e18;

Close solver fee rate caps use cumulative closed notional:

closeNotional = quote.closedAmount * quote.avgClosedPrice / 1e18;

This makes partial closes work naturally. If only half of a position has been closed, the close solver fee rate cap is based on that half. If the rest of the position closes later, the cumulative closed notional grows and can unlock more solver-fee capacity.

When a quote is partially opened, the operational fee cap is split pro-rata between the opened quote and the child pending quote. Any already-charged operational fee remains on the opened quote and reduces the cap left for the child, so a partial open cannot create more total operational-fee budget than PartyA approved. Solver fee rate caps are copied unchanged because each quote's notional is already smaller.

Accounting

A successful operational fee charge updates balances as follows:

allocatedBalances[partyA] -= operationalFee;
balances[operationalFeeReceiver] += operationalFee;

Open and close solver fees are still credited to the solver PartyB:

allocatedBalances[partyA] -= solverFee;
balances[partyB] += solverFee;

PartyB allocated balances are not touched. Fees are paid directly to free balances, making them separable from trading margin allocation.

Integration Flow

  1. PartyA sends a quote with one operational fee cap and separate open and close solver fee caps.
  2. PartyB locks and opens the quote with the fee-aware PartyBSolverFeeActionsFacet.openPosition overload when an open solver fee should be charged.
  3. For close, PartyA uses the existing close method; close solver fee caps come from the original quote.
  4. PartyB fills normal close requests with the fee-aware PartyBSolverFeeActionsFacet.fillCloseRequest overload when a close solver fee should be charged.
  5. For close-to-liquidation flows with solver fees, PartyB should call the fee-aware PartyBSolverFeeActionsFacet.fillCloseRequestToLiquidation overload. The legacy fillCloseRequestToLiquidation method is protocol-close-fee-only.

This keeps all solver-side fees tied to the execution that justifies the fee and to the solvency check for that execution.

The fee-aware functions are Solidity overloads of the legacy PartyB actions and appear next to them in the merged ISymmio ABI. Clients using merged-ABI tooling (for example ethers) must reference them by fully-qualified signature, e.g. openPosition(uint256,uint256,uint256,(...),uint256,uint256).

Edge Cases

  • Only the quote's PartyB can use fee-aware execution overloads.
  • Only a registered PartyB can set its own operational-fee receiver.
  • address(0) operational-fee receiver means fees are credited to PartyB.
  • Operational fees can only be charged through fee-aware open or close execution overloads.
  • Open solver fees can only be charged through the fee-aware openPosition overload.
  • Normal close solver fees can only be charged through the fee-aware fillCloseRequest overload.
  • There are no standalone external chargeOperationalFee, chargeOpenSolverFee, or chargeCloseSolverFee selectors.
  • Legacy quote APIs store zero solver fee caps, so solver fee charging reverts unless caps were explicitly approved.
  • Charges revert if PartyA allocated balance is lower than the requested fee amount.
  • The fee-aware openPosition overload reverts if PartyA would be liquidatable after deducting the requested solver fees.
  • The fee-aware fillCloseRequestToLiquidation overload subtracts the planned operational plus solver fee before calculating the maximum close amount.
  • Close fees are charged immediately before the close executes, with the rate cap evaluated against the cumulative closed notional including the pending fill. This keeps the fee transfer safe from final-close hooks (such as AccountLayer virtual-account cleanup) that deallocate PartyA's balance.
  • When PartyA is bound to the quote's PartyB and that PartyB is bindable, the fee-aware overloads skip the PartyA post-fee solvency check -- consistent with core bound-mode semantics, where the bound PartyB internalizes PartyA risk. Fee caps and the PartyA allocated-balance check still apply.
  • fillCloseRequestToLiquidation is kept only for backward compatibility and does not account for solver fees.
