BalanceChange Event Cleanup

v0.8.6 makes liquidation and clearing-house balance events describe the bucket that actually changes.

Summary

Some liquidation-time credits used to be emitted as realized PnL even when storage moved the amount into a more specific bucket, such as reimbursement, deferred balance, released pending fees, or LF. That forced indexers to infer accounting meaning from surrounding flow.

v0.8.6 makes those events follow the bucket that actually changes. The new enum value is REIMBURSEMENT_IN, and related liquidation/Clearing House flows now use existing specific types instead of overloading realized PnL.

Why Event Labels Changed

The old event stream often answered only "PartyA balance increased." For liquidation and Clearing House flows, that was not enough: reimbursement, deferred balance, released open fees, and LF are different accounting buckets.

  • Clearing House reimbursement credits: credits to partyAReimbursement emit REIMBURSEMENT_IN.
  • Pending-fee reimbursement: released open-fee reserves moved into partyAReimbursement emit PLATFORM_FEE_IN.
  • Deferred balance release: deferred excess returned to PartyA emits DEFERRED_BALANCE_IN.
  • PartyA liquidation fee: final settlement emits LF_OUT from the liquidated PartyA and LF_IN to the liquidation starter.

The shared idea is the same in every case: event labels should describe accounting movement, not just the fact that a balance increased.

BalanceChange Type Model

REIMBURSEMENT_IN is appended after DEFERRED_BALANCE_OUT. That keeps every existing BalanceChangeType integer stable, so consumers add the new trailing label without shifting older decoders: 

enum BalanceChangeType {
    ALLOCATE,
    DEALLOCATE,
    PLATFORM_FEE_IN,
    PLATFORM_FEE_OUT,
    REALIZED_PNL_IN,
    REALIZED_PNL_OUT,
    CVA_IN,
    CVA_OUT,
    LF_IN,
    LF_OUT,
    FUNDING_FEE_IN,
    FUNDING_FEE_OUT,
    DEFERRED_BALANCE_IN,
    DEFERRED_BALANCE_OUT,
    REIMBURSEMENT_IN
}

Clearing House distribution selects the emitted type from the receiver path:

  • PartyB receiver: credit partyBAllocatedBalances and emit BalanceChangePartyB(..., REALIZED_PNL_IN).
  • Liquidating PartyA receiver: credit partyAReimbursement and emit BalanceChangePartyA(..., REIMBURSEMENT_IN).
  • Non-liquidating PartyA or other receiver: credit allocatedBalances and emit BalanceChangePartyA(..., REALIZED_PNL_IN). 
if (maLayout.liquidationStatus[receivers[i]]) {
    accountLayout.partyAReimbursement[receivers[i]] += amount;
    emit SharedEvents.BalanceChangePartyA(receivers[i], amount, SharedEvents.BalanceChangeType.REIMBURSEMENT_IN);
} else {
    accountLayout.allocatedBalances[receivers[i]] += amount;
    emit SharedEvents.BalanceChangePartyA(receivers[i], amount, SharedEvents.BalanceChangeType.REALIZED_PNL_IN);
}

Consumer Impact

Event consumers should stop treating all liquidation-time PartyA credits as realized PnL. In v0.8.6, the event type carries more bucket information:

  • REIMBURSEMENT_IN maps to partyAReimbursement.
  • PLATFORM_FEE_IN can represent released open fees moved into the reimbursement bucket during liquidation.
  • DEFERRED_BALANCE_IN maps to deferred excess returned to PartyA.
  • LF_IN for PartyA liquidation finalization maps to the liquidation starter's allocated balance.

Existing enum values keep their prior numeric positions. Consumers that decode BalanceChangeType by integer should add the new trailing value without shifting older labels.
