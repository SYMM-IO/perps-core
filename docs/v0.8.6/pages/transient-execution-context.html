v0.8.6/Performance

Transient Execution Context

InstantLayer batches carried their authority in persistent storage flags, paying SSTORE to raise and lower them on every call. That authority now lives in EIP-1153 transient storage for exactly one transaction, saving roughly 22k gas per batch while keeping every deployed InstantLayer working unchanged.

Summary

An InstantLayer batch runs with temporary privileges on the Symmio core: the call is routed by InstantLayer, it may use atomic-open accounting shortcuts, and it may act on behalf of a delegated signer. Those three facts were stored in GlobalAppStorage as ordinary state, so every batch paid to write them on the way in and again on the way out, and they were only ever cleared because the caller remembered to clear them.

LibExecutionContext moves that authority into EIP-1153 transient storage, which the EVM discards automatically at the end of the transaction -- including on revert. A new ExecutionContextFacet owns the lifecycle, LibAccountLayerSigner mirrors the model for the AccountLayer diamond, and the persistent fields remain readable as a fallback so nothing that has not migrated changes behaviour.

This requires solc 0.8.34 with a Cancun EVM target. Chains without Cancun cannot run the transient path; the legacy persistent route is retained for exactly that reason.

The Three Pieces of Authority

"Execution context" is a deliberately narrow term here. It is not a caller address, and it does not replace signature verification. It is the temporary authority a batch carries, and it comes in three parts held in three separate places:

  1. The context word -- one transient slot packing "a scope is live", "routed by InstantLayer" and "atomic-open permitted" into three bits.
  2. The signer -- two transient slots, a value and an active marker. The reason for the pair is explained below; it is the single most misread part of the design.
  3. Per-caller snapshots -- one transient slot per address, used when a trusted router suspends the context across its own untrusted call.

All of it is shared by every facet reached through the diamond's delegatecall, which is what makes it behave like a transaction-wide global rather than a parameter.

The Live Context Word

Three bits of a single 256-bit word, held in a namespaced transient slot:

Bit Constant Meaning
0 INSTANT_CONTEXT_ACTIVE A scope is currently open.
1 CALL_FROM_INSTANT_LAYER This call is routed by InstantLayer.
2 INSTANT_OPEN_MODE Atomic-open accounting shortcuts are permitted.

Bit 0 looks redundant next to bit 1, because beginInstantLayerExecution always sets both. It is not. Bit 0 answers a different question -- not "does the caller have routing authority" but "is a scope open at all". That distinction is what every reader keys on, and it is why a scope opened with atomic-open disabled is still distinguishable from no scope.

Packing all three into one word is where the gas saving comes from: opening a scope is one tstore, where the old flags cost two SSTOREs to raise and two more to clear.

The Fallback Rule

Every public reader follows the same shape: consult the live scope, and only when no scope is open read the persistent field. 

function isCallFromInstantLayer() internal view returns (bool) {
	uint256 context = _instantLayerContext();
	if (context & INSTANT_CONTEXT_ACTIVE != 0) return context & CALL_FROM_INSTANT_LAYER != 0;
	return GlobalAppStorage.layout().callFromInstantLayer;
}

With no scope open the library is behaviourally invisible, which is what lets this ship without migrating every caller at once. isInstantOpenMode has the identical structure.

isTransientContextActive deliberately breaks the pattern and never falls back. The two are easy to confuse and are not interchangeable:

Reader Question it answers Falls back?
isCallFromInstantLayer Does the caller have routing authority? Yes -- a persistent flag can grant it too.
isTransientContextActive Is a transient scope open? No -- only bit 0 can answer this.

Callers deciding which storage mechanism to write -- notably ControlFacet.setSigner -- must use the second. Using the first would let a persistent flag steer them into writing transient state that no scope is going to clean up.

Why the Signer Needs Two Slots

The transient signer is stored as two transient words:

  • a value slot holding the address;
  • an active marker recording that transient storage -- not the persistent signer field -- currently owns the signer.

They are separate because of external calls. Before core hands control to untrusted code -- an affiliate hook, a token with callbacks -- it must clear the signer so the callee cannot act as the user. But it also has to remember which mechanism to put back. Clearing only the value while leaving the marker set is precisely the suspended state: transient storage still owns the signer, but no address is installed.

This is why restoreSignerAfterExternalCall checks a deliberately different set of slots in each branch, which reads like an inconsistency until the nested case is considered:

Suspended from Checks on return Why
Transient storage Both value slots empty. Marker not checked. The marker is legitimately either state: 1 if nothing touched it, 0 if a nested trusted scope opened and correctly closed itself, since closing writes the shared marker to 0.
Persistent storage Both value slots empty and marker clear. No transient scope was open at the boundary, so a set marker can only mean untrusted code opened one and left it open.

Both branches fail closed. Restoring on top of a signer the callee installed would bless that value for the rest of the transaction, so the boundary reverts instead.

One further consequence: configuredSigner() and signer() are not interchangeable. The first returns the raw value and can be address(0); the second falls back to msg.sender and therefore can never be zero. Access-control guards must use the first, because a guard written against the second would see msg.sender and conclude no signer was installed.

The Suspend Snapshot

When a boundary suspends the context it builds a second value. A snapshot is never written back into the live slot while the suspension lasts -- it is returned to the caller, or parked in that caller's own transient slot -- which is what makes reusing the low bits safe.

Bit Role
255 Marks a real snapshot. Set unconditionally so a populated snapshot can never be confused with the 0 sentinel meaning "there was nothing to suspend".
254 The suspended authority came from transient storage. This is the only discriminator restore uses to decide which source to write back.
1–2 The suspended routing and atomic-open flags, carrying the same meaning as in the live word.

Bits 1–2 keeping their live-word meaning is deliberate: it lets the transient branch recover the original context with a single mask rather than rebuilding it flag by flag. 

if (snapshot & EXTERNAL_CONTEXT_SNAPSHOT_TRANSIENT != 0) {
	_setInstantLayerContext(snapshot & INSTANT_CONTEXT_FLAGS);
} else {
	globalLayout.callFromInstantLayer = snapshot & EXTERNAL_CONTEXT_SNAPSHOT_PERSISTENT_CALL != 0;
	globalLayout.instantOpenMode = snapshot & EXTERNAL_CONTEXT_SNAPSHOT_PERSISTENT_OPEN != 0;
}

The two encodings do disagree about bit 0 -- a transient snapshot inherits it from the live word, a persistent one never sets it, because the persistent branch builds its snapshot flag by flag. That difference is inert only because nothing ever reads bit 0 back out of a snapshot; bit 254 alone decides interpretation.

Before writing a snapshot back, restoreExecutionContextAfterExternalCall requires both sources to be empty. The suspension emptied them, so anything present on return was installed during the untrusted call, and restoring over it would let a hook smuggle privilege past the boundary.

For cross-contract use -- AccountLayer calling out to an affiliate hook -- the router cannot hold the snapshot in memory across its own call, so core parks it in a slot derived from keccak256(namespace, msg.sender). The router therefore cannot choose what it restores, cannot reach another router's snapshot, and cannot suspend twice: a second suspend would overwrite the first, so it is rejected outright.

Lifecycle Rules

Three rules make the scope trustworthy, each with its own error:

Rule Error Reason
A scope cannot nest. TransientContextAlreadyActive Two batches must never silently share one grant of authority.
A scope that was never opened cannot be closed. TransientContextNotActive Makes an unbalanced teardown loud instead of silent.
A scope cannot end while a signer is installed. TransientSignerNotCleared A transient signer outlives the call unless cleared. Ending its owning scope would leave an identity every later call still reads, with nothing to attribute it to.

The third is the one worth internalising: it enforces unwind order, not tidiness. InstantLayer must clear its per-operation signer before closing the batch scope.

Compatibility and Rollback

An already-deployed InstantLayer cannot be changed, and redeploying one would invalidate its EIP-712 verifying address along with every template and signed operation. Instead both diamonds carry a per-caller adapter map:

  • Core: setLegacyExecutionContextAdapter(instantLayer, true) routes that caller's existing setCallFromInstantLayer and setInstantOpenMode calls into transient state, with identical calldata.
  • AccountLayer: setLegacySignerAdapter(router, true) does the same for that router's setSigner calls.

Enabling an adapter selects a storage mechanism. It does not grant the router any privilege, and it is refused while any persistent context or signer is still set, so a deployment can never have both mechanisms simultaneously believable.

Newly deployed InstantLayers use the native path directly and expose setTransientContextEnabled(false), which replays the exact historical setter sequence. Combined with disabling the two adapters, that is a complete rollback to persistent storage without touching a template or a signature.

The configure:transient-context Hardhat task performs the adapter configuration against an existing deployment, reads back both sides, and fails rather than reporting success on a partial configuration.
