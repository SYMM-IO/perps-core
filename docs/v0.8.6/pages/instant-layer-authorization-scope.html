v0.8.6/InstantLayer

InstantLayer Authorization Scope

The helper contracts accepted a global “inside an InstantLayer batch” flag in place of an authorization check. v0.8.6 checks the direct caller instead.

Summary

The MultiAccount and SymmioPartyB helper contracts accepted an ambient signal in place of a real authorization check: a global flag on the core diamond saying the protocol was currently inside an InstantLayer batch. v0.8.6 replaces that with a check on the direct caller.

What Changed

MultiAccount._call gates non-owner callers on a per-account, per-selector delegation map, and it accepted an alternative: 

require(
    delegatedAccesses[account][msg.sender][functionSelector] || ISymmio(symmioAddress).isCallFromInstantLayer(),
    "MultiAccount: Unauthorized access"
);

isCallFromInstantLayer() reads a single global boolean on the core diamond, GlobalAppStorage.callFromInstantLayer. The InstantLayer sets it true before executing a batch and false afterwards.

That flag answers “is the protocol currently inside an InstantLayer batch?” It says nothing about who is calling MultiAccount. While it is true, _call accepts any msg.sender, for any account, for any selector, and the delegation map is skipped entirely. Batches execute user-signed operations against arbitrary targets, so any contract that gains execution inside one — a hook, a callback, a token transfer landing on a receiver it controls — runs in a window where the delegation check is off for every MultiAccount sub-account at once. The storage comment names the shape of the risk itself: the flag is persistent state, not automatically reset, and its lifecycle is the caller's responsibility.

MultiAccount deletes the bypass outright; SymmioPartyB replaces the global flag with a check on the direct caller.
Contract Before After
MultiAccount._call delegation entry or isCallFromInstantLayer() delegation entry only
SymmioPartyB._call / adlClose isCallFromInstantLayer() ISymmio.hasRole(msg.sender, INSTANT_LAYER_ROLE)

The SymmioPartyB replacement asks whether the direct caller actually holds the InstantLayer role on core. That is specific and unforgeable, where the flag was an ambient mode anything executing in the window could ride.

The flag itself is not removed. callFromInstantLayer and the isCallFromInstantLayer() view still exist on core, and Accessibility still reads the flag so bound PartyAs can act while instant-actions mode is on. What changed is that the helper contracts no longer treat it as authorization.

Effect on Callers

Anything that reached a MultiAccount sub-account during an InstantLayer batch without holding a delegation entry now reverts with MultiAccount: Unauthorized access. The resolution is an explicit delegateAccess grant for the account and selector, which is what the delegation map was always for.

MultiAccount is legacy surface — affiliates track theirs under legacyMultiAccounts — but it is still live for existing users, so this affects real integrations rather than only new ones.
