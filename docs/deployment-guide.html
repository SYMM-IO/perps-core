Docs/Deployment guide

Deploying SYMMIO

How to work with the symmio operator CLI: one reviewed JSON file describes the whole deployment, one command executes it, and every step is resumable. This guide is the practical companion to deployment.md — read it once before your first deployment, then keep it open during.

Start without memorising anything

Run the CLI with no arguments. It reads the recipes, reports and checkpoints already in your checkout, tells you where the deployment stands, and offers the next useful step. Enter takes the recommendation; q quits. 

./symmio

It dispatches to the same commands documented below rather than reimplementing them, so every preflight gate, confirmation prompt and exit code is identical — and it prints the equivalent command before running it, so you pick up the vocabulary as you go. The rest of this page explains what those commands do and why, which is worth reading once before a live run.

It never deploys on its own. Interactive mode only offers choices; a live deployment still asks for the same risk-proportional confirmation. Without a terminal — CI, a pipe — it prints the getting-started commands instead of prompting, so nothing can be silently selected on your behalf.

How the pieces fit

Four artifacts carry a deployment. Understanding what each one owns explains almost every behaviour you will meet, including the ones that look surprising at first.

Artifact Owns You edit it?
Recipe
deployments/<name>.json		 All public intent: network, governance addresses, collateral, Muon, protocol parameters, and a mode for every component. Yes — this is the only file you author.
Digest A hash of the normalized recipe, pinned across the CLI → Hardhat boundary so the plan you reviewed is the plan that runs. No — computed.
Checkpoint
tasks/data/checkpoints/		 In-progress state: every contract address, every submitted transaction hash and nonce. This is what makes a resume safe. Never hand-edit.
Report
tasks/data/<chainId>/		 The outcome: addresses, verification status, health checks, and the authoritative manualActions list. No — it is your evidence.
Secrets never enter the recipe. The JSON holds only references like hardhat-keystore://NEW_DEPLOYER. Private keys, RPC URLs and explorer keys live in the encrypted Hardhat keystore, and resolved values are never copied into the plan, digest, checkpoint or report. In recipe mode neither the CLI nor Hardhat reads .env at all.

What a full run deploys

core is a bundle, not a single contract. Setting it to deploy produces the Muon verifier, the Core Diamond and its 32 facets, the AccountLayer diamond, and InstantLayer — then wires protocol parameters and templates. The three add-ons are independent. 

flowchart TD
    R[Recipe JSON] --> D{doctor}
    D -->|blocking failure| R
    D -->|ready| P[deploy --plan]
    P --> X[deploy]
    X --> C[Core bundle<br/>Diamond + 32 facets<br/>AccountLayer + InstantLayer]
    C --> B[PartyB]
    C --> S[SymbolManager]
    C --> E[ExpressProvider]
    B --> V[Explorer verification]
    S --> V
    E --> V
    V --> H[pending_handover<br/>exit 2]
    H -->|admin executes manualActions| X
    X --> K[complete<br/>exit 0]

The six commands

Everything runs through ./symmio, the checkout-local entrypoint. It needs no install step and no global binary. Commands with a green edge only read; commands with a coral edge can send transactions.

Read only recipe init Creates a recipe from the reviewed example. Refuses to overwrite unless --force.
Read only doctor Preflight. Names the exact JSON field for anything wrong. Costs nothing — run it often.
Sends transactions deploy Runs doctor, prints the plan, asks for confirmation, deploys, verifies. --plan stops before any transaction.
Read only status Re-proves the live on-chain state against the report. Never reports an unreadable probe as healthy.
Explorer only verify Retries explorer verification. --retry-failed replays only the records that failed.
Read only config Show, diff or export protocol parameters from an existing deployment — useful when mirroring a chain.
Two entrypoints, two jobs. ./symmio is the operator CLI. ./utils/pinned-yarn.sh is for package-manager work (install, link, run) and enforces the Yarn Classic pin. The older ./utils/yarn-classic.sh still works and forwards to whichever is right.

One-time setup

Use the checked-in toolchain. Do not regenerate the lockfile immediately before a deployment.

node --version                                    # v22.15.0
./utils/pinned-yarn.sh --version                  # 1.22.22
./utils/pinned-yarn.sh install --frozen-lockfile

Then store the three secrets once. They are encrypted at rest and prompted for when a deployment needs them:

./node_modules/.bin/hardhat keystore set NEW_DEPLOYER
./node_modules/.bin/hardhat keystore set RPC_ARBITRUM
./node_modules/.bin/hardhat keystore set ETHERSCAN_APIKEY

The explorer key is an Etherscan V2 key — one key covers Arbiscan and the other supported explorers. A preinstall hook enforces the package-manager pin even if someone bypasses the wrapper and runs npm install, because a dependency tree resolved by the wrong tool is not the tree that was reviewed.

Filling the recipe

./symmio recipe init --network arbitrum

This writes deployments/arbitrum.json with every operator decision left as a REPLACE_WITH_* placeholder, so the file cannot pass doctor before it has been reviewed. Fifteen values need a decision.

Field What it is
governance.admin Production multisig. Must differ from the deployer on a known mainnet — this is enforced, not advisory.
governance.feeReceiver Protocol fee recipient.
governance.liquidationInsuranceVault Economically active: excess normal-liquidation profit is credited here.
governance.softLiquidationPenaltyCollector Economically active: non-zero soft liquidations revert without a collector.
core.collateral.address The reviewed token. On Arbitrum, USDC is 0xaf88d065e77c8cC2239327C5EDb3A432268e5831.
core.muon.appId Muon application id.
core.muon.publicKey.x TSS public key X. Base-10 decimal, not hex — a 0x… value is rejected. Check parity too; it is preset to 0.
core.muon.gatewaySigners One or more gateway signer addresses. Duplicates are rejected.
partyB.signer PartyB operational signer for ERC-1271 verification.
symbolManager.operator Receives SYMBOL_ADDER_ROLE and SYMBOL_REMOVER_ROLE.
expressProvider.creditLine.muonAppId Muon app id for eligible-base attestation. The verifier defaults to "fromCore", resolved at execution time.
expressProvider.roles The bot address appears three times — OPERATOR_ROLE, LOCKER_ROLE, UNLOCK_ROLE — plus a separate SIGNER_ROLE. At least one operator is mandatory.
expressProvider.affiliates[].address The affiliate whose pool backs credit advances.
expressProvider.affiliates[].maxDebt Protocol-side cap in collateral decimals. 0 means no limit, not "cannot borrow".
The credit line moves real collateral out of Core. maxDebt and maxDebtBps are the only protocol-side ceilings on how much. Setting both to 0 means unlimited; doctor warns when it sees that. On a post-payout rollback the loss is booked to the affiliate ledger as bad debt and Core is not repaid on-chain — recovery is a governance action. Deploy an ExpressProvider only if that settlement model is what you intend, or set expressProvider.mode to "skip" and the other five components still deploy.

Two pre-filled values deserve a deliberate look rather than a nod: governance.maxLiquidationProfitPerPosition (100e18) and the whole core.protocol block, which carries the protocol parameters and the four ordered InstantLayer templates.

Running a deployment

  1. Preflight

    Read-only, exits non-zero on anything blocking, and every remediation names the exact JSON field to edit.

    ./symmio doctor --config deployments/arbitrum.json

    Keystore references are reported as deferred warnings — the dependency-free doctor cannot unlock them, so the Hardhat task rechecks the signer, chain, authority and explorer gates before it creates a checkpoint or sends anything.

  2. Rehearse on a fork

    fork-arbitrum is an in-process EVM backed by the real Arbitrum RPC. It reads live chain and token state, but every write stays local and disappears when the process exits. The upstream chain id is still 42161, so the mainnet safety profile is evaluated exactly as it would be live. 

    ./symmio recipe init --network fork-arbitrum
./symmio deploy --config deployments/fork-arbitrum.json --fresh

    Compare the fork recipe against the live one and require every public value except network mode and verification policy to match. A fork rehearsal does not prove explorer verification, live RPC reliability, real gas pricing, or multisig execution.

  3. Render the plan

    Stops after doctor and the dependency plan. Nothing is broadcast. Read the digest and the component table before continuing. 

    ./symmio deploy --config deployments/arbitrum.json --plan

  4. Deploy

    Risk-proportional confirmation is required interactively. For controlled automation, both flags are mandatory on a mainnet. 

    ./symmio deploy --config deployments/arbitrum.json

# non-interactive
./symmio deploy --config deployments/arbitrum.json --yes --confirm-network arbitrum

    Explorer verification runs inside the deployment as a gate, not as a follow-up step. It is also sticky: once any run requests it, a later --no-verify cannot downgrade that checkpoint.

Reading the exit code

This is the signal operators misread most often, so it is worth memorising.

0 Lifecycle complete. Deployed, verified, handed over, health gates passed. Done.
2 Contracts are deployed and verified, but reported admin/Safe actions are still outstanding. Not a failure. Execute the actions, then rerun.
≠0,2 Preflight refused, or the run failed. Nothing is assumed about on-chain state. Read the error; it names the field or the hash.

An ephemeral fork rehearsal may exit 0 while still printing pending_handover, because its simulated state disappears with the process.

Completing the handover

The authoritative list is manualActions in the report — the CLI prints it, with ready-to-paste to, value and data for each. Do not substitute a generic checklist for what your run produced. Typical actions:

  1. The admin calls acceptOwnership() on the Core Diamond.
  2. The admin calls acceptOwnership() on the AccountLayer diamond.
  3. The admin calls acceptOwnership() on the ExpressProvider diamond, when one was deployed.
  4. The admin calls registerExpressProvider(<address>) on Core.
  5. If the SymbolManager admin differs from the deployer, the admin grants the exact pending operator roles shown.
ExpressProvider always leaves actions pending, by design. The deployer is never granted PROVIDER_ADMIN_ROLE on Core, so registration is deferred to the admin multisig — which does hold it. Until registerExpressProvider lands, the provider cannot call advanceWithdraw and is inert.

After every reported action confirms, rerun the identical deploy command. It rechecks live state, runs the strict health gates, and flips the lifecycle to complete. 

./symmio status --config deployments/arbitrum.json

When something breaks

Rerun the same command without --fresh. That is the whole recovery story for the common case. The checkpoint is bound to the deployment id, chain scope, configuration and CREATE2 intent, so a mismatched resume fails rather than silently mixing two deployments. Contract creations are additionally bound to sender/nonce or CREATE2 salt, init-code hash and runtime bytecode — a timed-out creation that actually landed is recovered into the checkpoint instead of being deployed twice.

A timeout is not permission to start fresh. Check the transaction hash on the explorer, then resume. --fresh is refused outright while any submitted transaction still has an unknown outcome, and when it does run it archives the prior attempt under checkpoints/abandoned/ — it never labels an abandoned run as completed.

If you replaced a stuck transaction with a same-intent speed-up, bind the hashes explicitly:

DEPLOY_TX_REPLACEMENTS=0x<original>=0x<replacement> \
  ./symmio deploy --config deployments/arbitrum.json

The replacement must use the same sender, nonce, target, value and calldata. If the RPC no longer knows the original hash and both latest and pending nonces prove the nonce reusable, you may acknowledge that exact dropped hash with CONFIRM_DROPPED_TX_HASHES=0x…. Never reach for that while the transaction is still visible on any RPC or explorer.

For explorer failures specifically, retry only what failed, then rerun the deployment so the checkpoint can close its gate:

./symmio verify --config deployments/arbitrum.json --retry-failed
./symmio deploy --config deployments/arbitrum.json

Deploying one component

Add-ons can be deployed on their own against an already-proven Core. Generate a minimal recipe, fill its placeholders, and narrow the mutation scope explicitly. --only never silently rewrites recipe modes, and it never deploys Core implicitly. 

./symmio recipe init --network arbitrum --only expressProvider
./symmio doctor --config deployments/arbitrum-expressProvider.json --only expressProvider
./symmio deploy --config deployments/arbitrum-expressProvider.json --only expressProvider --plan
./symmio deploy --config deployments/arbitrum-expressProvider.json --only expressProvider

Valid targets are partyB, symbolManager and expressProvider. The generated recipe sets core.mode to reuse and points core.fromReport at the chain-scoped Core report; those exact bytes are folded into the digest and rechecked at task startup, so changing the dependency report after review fails closed. Component runs own a separate checkpoint and report, and cannot claim the whole protocol was deployed.

Core is a bundle. --only core does not exist. To deploy just the Core bundle, set partyB, symbolManager and expressProvider to "skip" and run without --only.

Gotchas that cost hours

Money

maxDebt: "0" and maxDebtBps: 0 mean unlimited, not zero.

Read as "no cap on that axis". An uncapped credit line can advance the entire eligible base out of Core.

Blocks run

core.muon.publicKey.x must be a base-10 decimal string.

A hex 0x… value is rejected with a schema error that is easy to misread as a bad key.

Blocks run

A create2.factoryAddress carried over from a live recipe breaks local and fork runs.

The address has no code on a simulated chain, and the deployment refuses to silently switch address strategies. Keep the create2 block out of local and fork recipes, or point it at a factory deployed on that chain.

Confuses

Exit code 2 is a success, not a failure.

It means deployed and verified, handover outstanding. Automation that treats any non-zero exit as a failure will page you for a healthy run.

Confuses

Vanity addresses are configured in the top-level create2 block, never in the environment.

Set create2.groups (diamonds, facets, libraries, peripherals) and optionally create2.overrides keyed as core/PartyAFacet. Declaring any pattern without a reviewed create2.factoryAddress is a validation error rather than a silent fall back to ordinary CREATE. The run prints a mining cost table and refuses to start if the total exceeds create2.miningBudget. Etherscan verification of a CREATE2-deployed facet should be confirmed on a testnet before a mainnet run, since its address no longer derives from the deployer nonce.

Confuses

.env is not the deployment interface.

In recipe mode neither the CLI nor Hardhat reads it. If a value is not in the recipe or the keystore, it is not in the deployment.

Confuses

Symbols are not seeded by deploy.

Creating trading symbols is a separate post-deployment operating step.

Where everything lives

Path Contents
deployments/<name>.json Your versioned deployment recipe. Commit it — it is reviewed intent.
tasks/data/<chainId>/deployment-report.json Full-run report: addresses, verification, health, manualActions.
tasks/data/<chainId>-fork/ Isolated fork records. A rehearsal never overwrites live evidence.
tasks/data/<chainId>/components/<recipe>/ Component-only reports, with prior attempts under history/.
tasks/data/checkpoints/ In-progress state. completed/ and abandoned/ hold finished attempts.
deployment/deployment-recipe.schema.json Machine-readable recipe contract. Editors that honour $schema will autocomplete against it.
deployment/examples/arbitrum.v1.example.json The reviewed starter every recipe init is generated from.

The whole thing, in order

./utils/pinned-yarn.sh install --frozen-lockfile

./symmio recipe init --network arbitrum
# edit deployments/arbitrum.json — replace every REPLACE_WITH_* value

./symmio doctor  --config deployments/arbitrum.json
./symmio deploy  --config deployments/arbitrum.json --plan
./symmio deploy  --config deployments/arbitrum.json      # exit 2 = handover pending

# admin executes the printed manualActions, then:
./symmio deploy  --config deployments/arbitrum.json      # exit 0 = complete
./symmio status  --config deployments/arbitrum.json
